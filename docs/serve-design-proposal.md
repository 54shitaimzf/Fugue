# serve 与只读并行：待审批提案

状态：**提案，尚未批准、没有协议冻结或产品实现**。对应 ROADMAP § 5 的两项前置审批。
这份文档不能替代审批，也不能修改 M0 事件联合或架构契约。即使前面索引达标，审批未过
也不启动 0.4.1–0.5.0。下面是可供一次完整审查的最小方案与验收计划。

## 1. 单写者与 round.lock

- stdio serve 绑定启动它的客户端，不作为常驻系统服务；断开停止接受新请求，收尾已接受操作，
  显式释放句柄/锁，闲时自退。超时不能通过静默丢弃已发生的权威写入伪造成功。
- 只读 status 与日志尾随不领写者序号、不持有 round.lock；只从既有 git/M0 推导。
- 变更命令共用既有命令语义，不再做一份 serve 私有状态机。一次变更由同一串行入口执行，
  写句柄整个命令寿命持有该 writer 的栅栏，不是只在 append 时持锁。`round.lock`
  就是 M0 的 `writer=round` 栅栏（`lockFileOf(root, writer)`，即
  `<root>/.fugue/log/<writer>.lock`——与日志同目录同名、只换后缀），**不是另加一把轮锁**。
  同一已接受写命令不能重复获取这把锁、嵌套打开写句柄，或在命令的多个步骤之间释放后再拿。
  serve 不把所有 writer 变成一个全局写者，也不把进程驻留等同于永久锁定整轮。
- 同一轮另一个变更请求遇锁返回明确的 busy，不抢锁、不推测锁过期、不绕到直接日志追加。
  不同 writer 的合法并发仍遵守现有 M0 `(seq, writer)` 合并规则与 ref CAS。
- 首版只规定安全结束，不批准后台守护、远程网络监听、认证扩张或新的持久状态。

须审批的选择：以上按整个命令持锁/串行变更的所有权与寿命，是否满足单写者纪律；客户端死亡时
已接受操作的停止/收尾边界。精确方法/错误码须在批准后再冻结，而非由这份提案暗中定稿。

## 2. 只读并行的事件与回执次序

- 首版只有明确无权威写入、无执行副作用的工具可加入只读批次；写、物化、执行、交接等
  保守串行，不能因为名字像读操作就并行。并行数/待接收队列必须显式有界。
- 同一批次固定 View 基点；若期间发生写入，不能拼接两个代的结果。须明确重试或整批失效。
  写请求只能在前一个只读批次收尾后进入，不能在批次中抢先改变 View。
- 给模型的回执按原调用顺序归位，执行完成次序只作为瞬时进度；渲染器不塑造事件模型。
  若审批后的协议需要调用标识/开始结束关联，先设计兼容模式、再走冻结事件审批，不能
  把瞬时进度冒充已经可重放的 M0 成本事件。
- M0 单 writer 仍串行追加，保留现有合并全序；不宣称日志合并顺序就是工具完成的墙钟顺序。
  并行归属、失败/取消、批次暂停与单步的持久表达需随协议审批明确，现有未知量仍未知。
- 门视图浓缩件是日志/既有状态的纯函数，不额外保存一份事实，也不把可丢的模型进度
  当可恢复判据。成本台账的冻结事件扩展是另一道未批准门，不由 serve 提案代为批准。

须审批的选择：模型回执保持调用顺序、实时完成进度允许交错、M0 维持每 writer 序号；
任何新的持久调用关联字段，以及暂停/单步的精确边界。

## 3. 批准后的验收，不是本次已完成的结果

1. 版本化 stdio JSON-RPC 方法映射既有 `--json` 动词；未知版本/方法明确拒绝，样例客户端
   走通 status 与日志尾随，客户端渲染选择不改变事件联合。
2. 两个客户端争同一 writer/round 时恰一个合法写入；失败方不领重复 seq、不留下半份日志。
   只读附着不阻塞合法变更；断线/超时可重放已完成写入，没有泄露锁/进程/句柄。
3. 控制不同完成顺序，模型回执仍按调用序；只读批次与串行参考逐字节等价；写工具
   负对照一旦混入并行池测试应红；View 变代不能制造混合快照。
4. TUI 没有对内核/权威写入的直连依赖。lint 式断言加负对照，偷偷恢复直连必须红。
5. 门浓缩件从同一日志重复计算一致；缺失进度不改变门判决。多调用墙钟对照在合格环境
   记录，没有验收读数时不宣布 0.5.0 完成。

本次只记录待审方案。ROADMAP 原门、M0 架构、产品代码与默认行为均未改动。
