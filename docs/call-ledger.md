# 0.3.0 取数准备：从旧账派生逐模型调用台账

这一增量只读既有 `llm/call` 事件，不扩展冻结的 M0 事件面、模型协议、Runtime
或 Probe 契约，不另建产品日志。它给 T18/T11 一个可复核的模型调用基线，
**不声称完成了逐工具耗时与 token 成本台账**。

```sh
node tools/call-ledger.js <工作区根> [最多保留的调用行数]
node tools/test-entry.js fast src/probe/call-ledger.test.ts
```

开发出口吐 JSON schema 1。默认最多保留 5,000 行，仍报告日志里模型调用的总数
和是否截尾；允许 0 到 1,000,000 的整数。新增开发专用快照读口不另攒全量事件数组，读取时
不拿写锁、不修日志尾、不创建 `.fugue`，输出由相同源日志确定。

**源行与句柄的新增预算也明确封顶。** CLI 使用 `readLogSnapshot`：最多打开 128 个
writer，每次读取最多 64KiB，完整行上限 1MiB，保留每个 writer 的一个归并头以及当前行/块。
新增保留量为 O(writer 数 × 行上限)，不是整份历史，也不是所有 writer 共用一个 1MiB。
台账结果另受 maxRows 限制；字符串解码、事件对象和 JSON 输出仍有各自开销，以上不是 RSS 上限。
目录枚举沿用 M0 的 writers()，仍先递归保留全部名字，再执行 128 个 writer 的准入限制；
因此不能称任意目录结构下的总内存都固定有界。

完整的预算超限行或 writer 超限明确报 `LogReadLimitError`，不把合法日志说成损坏，也不
静默遗漏。未终止尾段仍忽略，即使超过行预算也不会攒下整段或截断它。完整坏行仍报原
`LogCorruptError` 与 writer/物理行号；fromSeq 与输出行数限制都不能绕过坏行校验。
缺少日志时给空账，不暗建目录。

快照先验证所有选中完整行，再第二遍按原 `(seq, writer)` 归并；writer 内沿用物理顺序，
不增加手写序号的拒绝规则。FD 固定住已打开的文件；大小与纳秒修改/状态时间改变时明确
拒绝，调用方可重读，不同时跟随正在追加的历史。下一次读会看到新追加及新 writer。
这些检查是文件元数据观察，不能证明一个恶意同权限写者没有改动并还原全部元数据。
这不是原子文件系统快照。

本批仅替换开发脚本的读口。产品 `openLog.readMerged()` 的完整解析缓存、M0 三个方法、
日志编码、写者锁与 TUI 轮询保持原实现；不会把大日志内存改进说成产品热轮询更快。
两遍解码和逐行快照检查增加 I/O，速度与内存的实测取舍单独记录。

每条调用用 `writer + seq` 指到唯一原事件。同一 agent、同一步编号的多条事件
各留一条，不悄悄去重。记录模型/协议、公布工具数、请求调用数、提供方用量与
结束原因；上游拒绝时的状态码（`status`，成功是 null）与重试状态码（`attempts`）只在源事件确实带着它时出现。

## 能说明和不能说明什么

- token 的范围是**整个模型调用**。不把一条响应的 token 平均分给它请求的工具
- 提供方的 0 保持 0，缺失保持 null。旧账缺少的字段和无效计数不做字符串强转
- `reasoningTokens` 是 output 的明细，保持单列，不冒充额外收费的第五类 token
- `toolMs`、`toolArgumentBytes`、`toolReceiptBytes` 恒为 null：旧账里没有它们
- `run/end.ms` 是执行动作的事实，不能冒充 read/grep 等每一条工具的耗时
- 用量是提供方实际报告的这一条调用；没有记录的失败尝试耗费、货币金额、
  逐工具名字、请求/回执字节和缺失状态码都不推算
- 不导出原参数、回执正文、响应头或其他日志内容，只导出这里列明的字段

要把真实逐工具事实持久记录后再重放，需要经批准的事件面扩展；本增量没有
借一份「测量文件」绕开该要求。全版 0.3.0 成本目标仍有这个明确的缺口。

## 检查

定向测试验证模型级 token 归属、未知/零的区别、交错 writer、重复 step、部分
失败、精确行数上限、流/数组重算一致、独立输出数据，以及真实 CRC 日志的纯读、
半行尾不变和不泄漏未公布字段。重复读取同一日志产生相同 JSON；输出可以作为
开发读数附件保存，删除后随时重建，不是真源。
