# Optional current-View cohort queries

`createViewCohortLookup(view, enumerate, store)` connects the bounded cohort artifact to the existing `grep` candidate seam (ROADMAP § 4 / 0.3.3). Pass the returned handle as `HostOptions.cohortIndex` to `createToolHost` for that exact View object. The adapter is privately bound to that object; another View or a caller-constructed port receives the existing scan path. The option is absent by default. If both index options are supplied, the valid cohort option takes precedence over `blobIndex`.

The first supported query in a View generation captures a bounded enumeration and its current file BlobIds, deduplicates paths and IDs, and reads one artifact for that exact set. Concurrent admitted queries share this load. The validated artifact and its private path-to-BlobId snapshot are retained as one generation-owned proof. Later batches reuse both, without repeating per-path metadata reads. A miss is also retained until the generation changes, successful preparation occurs on this handle, or the caller creates a new handle. Any unavailable, corrupt, unsafe, over-budget or wrong-set artifact returns all original candidates. Queries never fetch source blobs, build, or publish an index.

Candidate decisions use primitive identities captured from this exact View's `stat` calls, once per distinct enumerated path. The snapshot is private and never accepts caller-supplied path metadata. Only strict negative membership excludes a known file; unsupported requirements, missing metadata and paths outside the snapshot stay in the original ordered batch, including duplicate paths. Any base/rev change during enumeration, disk IO or metadata work restores the whole batch. A generation change starts a new snapshot and artifact selection, so edits, rename, removal and recreation cannot inherit an old path identity. The cached membership loop has no awaits or metadata calls; it still checks generation and close before returning. This is a per-batch check, not an atomic snapshot of a whole multi-batch search; files added outside the original tool enumeration retain its existing coverage semantics. The original regex, real content reads, output modes, early stopping and incomplete-enumeration receipts remain authoritative.

Preparation is explicit caller-paid work: `await handle.prepare(readBlob, options?)`. The callback selects immutable Git objects by complete BlobId, never materialized paths. New source windows are copied using intrinsic typed-array bounds and verified by `buildBlobIndex`; no subclass length/offset/buffer getter or iterator supplies a budget or content boundary. Complete records reused from a prior validated artifact plus complete newly verified records build one complete cohort. A failed source hash, generation change, unsupported source, dictionary/postings/byte cap, write failure or close returns false and never installs a partial membership proof. A successfully written old artifact may remain if the View changes during publication; its immutable ID-set key cannot be used as the new generation's artifact.

Incremental preparation (ROADMAP § 4 / 0.3.2) retains at most one prior opaque artifact from a successful controlled read or verified preparation. A View change invalidates query decisions but leaves that artifact available as an immutable preparation seed. `cohortBlobRecords` traverses its bounded dictionary/postings once, recovering exact sourceBytes/textUnits and COMPLETE sorted tables only for matching current BlobIds. Missing IDs get no record and must fetch/hash their source; they never receive an invented empty table. Returned tables are frozen owned arrays; arbitrary caller records or cloned handles cannot supply a reuse proof. Renames, mode changes, aliases and removal therefore require no unchanged source reads. A changed identity requires its own verified source. The output artifact still uses the exact current ID-set key and unchanged binary format.

For restart reuse, `options.previousBlobs` is a bounded dense hint for an earlier set. It is captured before awaits; the adapter performs one normal exact-set `store.read` and applies the same opaque extraction. Corrupt, missing, wrong-set or unsupported artifacts provide no reused records and preparation falls back to verified sources. The hint does not carry tables or authority. `options.prefetchBlobs` can call the caller's Truth batching port for new IDs only, in frozen batches of at most 128. Each batch is consumed before the next hint, preserving bounded source-cache use; a failed hint still performs every required hash-verified source read. Query methods never call either callback. Concurrent preparations share the first accepted preparation and its captured inputs.

The prefetch ceiling bounds candidate count. Individual blob sizes, physical IO, source-cache policy and memory allocated by the callback belong to the caller. The 64 MiB aggregate governs verified preparation inputs; it does not impose a whole-prefetch byte or process-memory ceiling.

Bounds are independent: 5000 enumerated paths, 4096 distinct blobs, 128 paths/required UTF-16 trigrams per query batch, 64 MiB aggregate source bytes during preparation, and the codec's 200,000 dictionary grams / 2,000,000 postings / 32 MiB artifact limits. The aggregate charges reused descriptors as well as new intrinsic source windows; reuse cannot evade it by reducing physical reads to zero. Extraction checks selected metadata totals before allocating tables. Dense indexed snapshots capture and validate one safe-integer length; iterators and sparse inputs cannot enlarge admission. At most four operations are admitted, with no wait queue. One preparation is shared; invalid or saturated admission falls back. The one retained prior artifact, bounded current-generation path map and in-flight owned records have additional decoded memory overhead, so the byte limits are not a whole-process heap bound.

`close()` immediately prevents new admission, drops retained artifacts and query snapshots, and observes every accepted query/preparation until it settles. Source and prefetch callbacks must settle; there is no hard cancellation of already-started source or filesystem IO. The caller separately owns `store.close()`, after closing the adapter. Preparation does synchronous codec work on the caller's execution thread and must be accounted outside the measured foreground query. `stats()` reports queries, artifact reads, source calls, reused complete records, prefetch hints, cohort builds, fallbacks and current admission; callback counts do not imply a count of actual Git spawns.

The adapter tests cover a fresh one-artifact disk read, paid preparation, absent/throwing/wrong-set fallback, generation rollback, exact View branding, dense input ownership, one-length capture, intrinsic source-window admission, shared preparation and bounded close observation. The prior proxy-length negative control performed 10,000 indexed reads after admitting a one-element array; the repaired capture performs exactly one. Real View receipt equivalence and 16 MiB cold-path measurements are separate integrated acceptance. This implementation supplies no default-activation, <50 ms, genuine live recording or strict sandbox certificate.

Incremental focused tests compare reconstructed records byte-for-byte with verified source-built v1 records (including SHA1/SHA256, empty, surrogate and replacement-character sources). Source-call controls prove unchanged/rename/mode/removal reuse is zero, a changed or recreated identity reads once, and fresh restart reuse performs one artifact read. Other controls cover corrupt prior fallback, unsupported hints, bounded failed prefetch progression, aggregate reused+new budgets and held stale/close cleanup. Structural inflated-metadata fixtures test budget refusal only; checksums/shape are not source authentication. Integrated incremental timing and real View receipts are recorded separately on the exact source composition.
