# 0.2.5 增量：同一视图代复用文件清单

这一步落实路线图 § 3 的「walk 清单按视图代缓存」部分，不改变工具目录、
日志事件、冻结的 View 契约或 grep/glob 的回执字节。`read` 窗口下推属于另一增量；
版本号和整版验收仍留在收口点处理。

## 缓存边界

- 每份 `ToolHost` 只保留一份视图代的派生清单；键是同一份 View 的 `base + rev`
- 同代并发读复用一次遍历，后来的调用得到独立数组，不会被上一位调用者改坏
- 写、改名、改权限、删除和墓碑后的重建推进 rev，下一次调用重新枚举
- 原有深度 24、文件数 5,000、目录顺序和不跟随软链/gitlink 的规则不变
- 枚举失败不缓存；旧请求晚完成或晚失败也不能清掉新一代的缓存
- 枚举期间视图变化，不把这一份结果留给后来的调用。它沿用原有逐目录读的
  并发语义，不声称提供一份原子快照
- 不落盘、不增加真源、不共享不同宿主的缓存，不改变执行面的物化清单

`src/tools/walk.ts` 是不认识日志、真源和执行面的纯读帮助模块；产品接线在
`createToolHost`。原来的 MAX_ROWS 截尾呈现保持不变，路线图 0.3.0 的如实报告另做。

## 复现与证据

```sh
node tools/test-entry.js fast src/tools/walk.test.ts
node tools/test-entry.js fast
node tools/test-entry.js all
node tools/bench-walk.js
FUGUE_ROOT=<修改前的 checkout> node tools/bench-walk.js
```

定向测试覆盖缓存命中、独立数组、视图代变化、不同宿主、顺序与边界、失败重试、
遍历中的变更、旧请求晚返回，以及真实内存 View 的写/改名/改权限/墓碑/重建。
负对照把产品宿主换回原实现：热 walk 的 list 调用数是 4 而不是 2，断言失败。

固定基准是 32 个目录中的 256 个内存视图文件，不改工作树、不启动模型或执行面。
2026-10-01 云工作区的机制读数：修改前首次/再次 walk 都枚举 33 次；修改后首次
33 次，再次 0 次；新增另一目录后重走 34 次，并读到第 257 个文件。冷热候选完全相同。
墙钟由脚本报告，不作为测试阈值，也不冒充一等档 ext4 的验收性能常数。
