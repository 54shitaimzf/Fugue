# 当前装配约束的常驻诊断

本批按 `design/ROADMAP.md` § 3 的 0.2.7①，在已发布的 0.2.6 实现上补证人。它没有把 `checkConstraints` 接入发送路径，也没有改四条判据、协议、事件或模型请求。

运行：

```
node tools/test-entry.js real src/assemble/constraints-state.test.ts
```

测试为每个案例创建独立 Git 仓库，用显式的 Git 身份与配置环境初始化。项目方针逐字读取当前仓库 `AGENTS.md`，配置经产品 `readConfig` / `stateWithState`，文件、树与提交经真实 `Truth` 读取，段值经 `sourcesFor` / `assemble`。两条运行时案例使用真实 M0 日志与 `Runtime.step`，模型响应是本地脚本，不出网、不取凭据。初始化失败和正常退出都关闭自己持有的句柄、清理临时目录。

## 已暴露的差异

1. 路线图明确指定的两处文档工作区指针已改成按工作区位置与文件名引用。但开发指南其余部分仍有 `/home/ubuntu/fugue` 等运行示例；产品按原文读取方针，`checkConstraints` 会把它报告为 A 区绝对路径。这不是「零违反」验收，测试明确保留这个诊断。不能把测试里的方针另换成干净常量，或为了通过测试把整份开发指南悄悄改写。
2. `Runtime.step` 的积累段 `turns` 确实保留旧项并追加新项，A/B 字节不变。但 `信号摘要` 与 `上一步结果` 位于它后面，正常有输出的一步会在整段 C 的旧尾部之前插入新轮次。现有 `checkConstraints` 比的是**整个 C 区**的前缀，所以会报告 `append-only`。已接受的 `src/runtime/step.test.ts` ② 也明确区分了这两种性质。本批用真实非静默步骤保留这一证据，没有手造 Prefix 让它看起来通过；静默步骤另证前后产品前缀没有新增违反。
3. 环境检查对当前宿主名和进程号做文本匹配。在进程号较小的环境，指南里的章节号或示例数字也可能命中。测试保留实际环境事实，允许这类已报告的 `env` 诊断，不把它计成干净装配。

注入用例把物化路径放入 A/B/C，把真实宿主名和进程号放入系统状态，把带 `digest` 的原始信号放入信号摘要，分别要求对应诊断；实际运行时状态的中部重写也必须触发追加约束。所有正反两侧都走产品源与渲染器。

## 最小待定事项

0.2.7① 的完整零违反验收还需要明确：项目方针是否继续完整携带开发指南里的宿主运行示例；「只追加」的诊断对象是 C 内的积累段，还是要改变整段 C 的排布与替换规则。这两处决定应与架构 § 8.11、现有运行时性质一致，不能靠删掉 `previous` 参数或只跑静默步骤回避。

本批只改路线图已指定的两处指针。它改变了实际 A 区字节，仍须按路线图 § 10 进行前缀录制与审批；本地脚本、历史录音或离线兼容重放都不构成新的真实提供方录制。这里没有改任何录音或用量，也不宣称 0.2.7 已收口。

## 本批验证

新 real 文件 5/5；现有 `assemble.test.ts`、`sources.test.ts`、`sources-state.test.ts`、`constraints.test.ts` 四文件 fast 组 27/27。把新文件放到原始 0.2.6 方针上，四条方针相关案例变红（1/5 通过、4/5 失败），证明两处指针修改没有被测试常量掩盖。注入路径案例还要求回报具体注入路径，不能借原有开发示例的诊断冒充通过。
