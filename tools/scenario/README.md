# 标准测试题（`tools/scenario/`）

这个目录用来回答一个问题：**这一版改完之后，赋格到底能不能把活干对？**

做法类似考试：出题人先准备好题目和标准答案，让赋格去做，做完后拿它实际改出来的文件和标准答案比对。整个判分过程不需要模型参与。

为什么需要这个？在此之前，我们只能检查两类东西：

1. **流程有没有正确执行**，比如测试数据对不对、文件是否逐字节一致、停下来的原因对不对；
2. **模型自己选的检查有没有通过**。

但第二类有漏洞：模型可以挑一个永远会通过的检查，这样结果总是「通过」，其实什么也没证明。所以光靠这两类，没法知道活到底干对了没有。

## 怎么运行

先进入仓库目录（`cd ~/fugue`），然后：

    sh tools/scenario/board.sh --selftest                  # 离线自检：确认判分逻辑本身是对的（不花钱）
    sh tools/scenario/board.sh --live --runs 3             # 调用真实模型：每道题连续跑 3 次
    sh tools/scenario/board.sh --live --runs 5 --gate-only  # 只跑到「等你确认任务列表」那一步就停，用来多次采样任务列表的通过率（便宜）
    sh tools/scenario/board.sh --live --case "改码 · 单文件（最小的一案，反复采样用）"   # 只跑指定的一道题
    sh tools/scenario/board.sh --stub                      # 不调用模型，只检查准备环境和判分这两部分能不能跑通
    sh tools/scenario/board.sh --live --out /tmp/盘-01      # 指定结果保存到哪个目录

关于 `--stub`：它**完全不调用模型**。但负责拆任务的那一步没有「假模型」可用（除了 `--wire-in` 回放和 `--judge` 之外，都会真的调用模型），所以 `--stub` 模式直接让它在第一步就被人工叫停（相当于 `--judge`，一步也不执行）。这样它只能检查三件事：环境准备、判分逻辑、结果记录。每次运行都会被记为「被退回」，统计表里的四列用量数据全部是 0。

## 由哪些部分组成

| 内容 | 位置 |
|---|---|
| 题目定义，包括：初始代码（`base`）、目标描述（`goal`）、可以使用的操作（`actions`）、**标准答案**（`answer`）、**一份应该被判为正确的参考结果**（`solved`）、出题人自己的检查命令（`observes`）、这道题覆盖了哪些环节（`covers`） | `tools/scenario/cases.json` |
| 判分逻辑及其六个测试。判分**只读**：它只看一份文件快照，不读写磁盘、不联网、不写日志 | `src/probe/board.ts`、`src/probe/board.test.ts` |
| 运行流程、判分、把结果写成统计表的一行 | `tools/scenario/board.sh`、`tools/scenario/board-node.ts` |
| 统计表（用 Tab 分隔，每次运行占一行） | `<out>/ledger.tsv`；每次运行的完整现场保存在 `<out>/run/<题目>-<第几次>/` |

## 五条原则

1. **答案只规定结果，不规定过程。** 不限制它怎么拆任务、分几步改、用什么工具。怎么做是模型自己的事。
2. **没有任何判分依据，就算不通过。** 这和 `src/merge/accept.ts` 的规则一样：「没法判断的，不能算通过」。
3. **没跑起来的不判分。** 如果 `work.json` 是空的（说明产品或配置一开始就拒绝执行了），就记为「没有结果」，并附上拒绝的原因。不要拿一份根本没改过的代码去判分，那样会得出错误的「失败」结论。
4. **用量数据从日志里重新计算**（用 `statusOf`），不采信模型自己报告的数字。出题人的检查命令（`observes`）是出题时就写好的，和模型自己选的检查无关。
5. **判分逻辑本身也要经过验证。** `--selftest` 会用每道题的参考结果（`solved`）和初始代码（`base`）各判一次：前者必须判为通过，后者必须判为不通过。另外还有三个反向测试：把参考结果改错、删掉答案、把答案清空。每一种都必须导致判分失败。

## 统计表的格式（15 列）

`题目 · 第几次 · 在确认环节被退回 · 正常收尾 · 自选检查结果 · 标准答案结果 · 出题人检查结果 · 冲突 · 被拒绝 · 越界 · 调用次数 · input · cacheRead · output · 写回`

（表头实际写作：`案 · 趟 · 门退回 · 停因收敛 · 验收 · 已知答案 · 观察 · 冲突 · 拒绝 · 越界 · 调用 · input · cacheRead · output · 推进`）

**每次运行的步数上限是多少？** 看 `$OUT/decl/<题目>/meta.json` 里的 `maxSteps`。如果运行时用 `--max-steps` 改过上限，这个文件里会有记录：`declaredMaxSteps` 是题目原本规定的上限，`maxStepsOverridden` 表示上限被改过。每次运行的输出里也会显示这个数字。

改上限只是为了测量「不限步数时它自然需要几步」，**绝不能用来把失败的结果变成通过**（设计文档 5.9.2 节禁止的就是这种做法）。

## 目前的测量结果

以下都是调用真实模型得到的结果，原始数据记录在对应的提交信息里。

**「两个子任务改同一个文件」根本走不到合并冲突那一步。**
我们按这个思路设计过一次第三道题。结果 `round run` 在合并之前检查写入范围时就直接拒绝了，报错是 `merge：合并前的写入集预检不放行：r1.implement.1 与 r1.implement.2：src/counter.js ↔ src/counter.js [implement × implement]`，**一次模型都没调用**。所以要测合并冲突，首先得想办法让流程能走到那一步。

**明确了「负责拆任务的助手什么时候该停」之后。**
两道题各跑 3 次，用同样的标准衡量：改进前是 2 次里 2 次都在确认环节被退回；改进后，**6 次里有 4 次顺利走到了确认环节**（停下来等人确认任务列表）。另外两次仍然被退回，但原因变了：一次是走了 4 步自己停下，但任务列表是空的；另一次是它试图往 `src/fields.js` 里写东西，被 `plan-scope` 规则直接拒绝了。「改码 · 单文件」这道题有两次拿到了结果，**标准答案都通过了**。

**用 `--gate-only` 连续测了四次**（每次每道题跑 5 次，都只跑到确认那一步）：
结果依次是 **4·2 → 6·4 → 7·3 → 7·3 → 7·3**（每组数字的意思是「顺利走到确认环节的次数·被退回的次数」）。单看一道题，数字在 2 到 4 之间来回波动；两道题合起来，走到确认环节的比例始终在 60% 到 70% 之间。**这么小的样本量，分辨不出 10 个百分点左右的差别。**

这期间做了四项改进，每项都在对应的提交里附有原始输出：
- `bd46b28`：把「要交付什么」和「边界在哪」这两句话加进发给模型的第二段内容（B 区）。结论是没看到效果。
- `3563183`：操作被拒绝时，提示信息里多加一句「这次还差什么没做」。
- `6a0e82e`：告诉模型已经配置好的操作时，连同它具体会执行什么命令一起说明。
- `0eb34b2` 和 `ac8ca59`：修正了路径格式的问题。`read {"path":"."}` 不会再让整次运行失败；`ownedPaths` 字段的格式说明里，把 `isRelPath` 的规则写完整了。

**比「有没有被退回」更有用的指标，是「第几步开始写任务列表」。**
这个数字可以离线从日志里算出来：看 `llm/call` 记录的 `outputTokens` 就行。前面探索项目的几步，每步输出 60 到 370 个 token；真正写任务列表的那一步，输出 400 到 3400 个 token。两个区间完全不重叠，很好区分。

测下来，上限 8 步的那道题，一般在**第 5 到 8 步**才开始写（好几次就是最后一步）；上限 6 步的那道题，在**第 3 到 5 步**开始写。所以这些失败其实是同一个原因：**步数都花在探索项目上了**，到最后两三步才开始写任务列表。这个指标不用花钱，离线就能算。

**真正卡住它的是步数上限。**
我们用 `--max-steps` 放宽上限，两道题各跑 5 次做对比：
- 按题目原本的上限（8 步和 6 步），结果分别是 **3·2 和 4·1**（走到确认环节的次数·被退回的次数）；
- 上限放宽到 16 步和 12 步后，变成了 **5·0 和 5·0**，每次都是自己正常结束的（停止原因是 `end-turn`，也就是 `收工：natural（收敛）`）。

而且多给的步数它**并没有全用掉**：10 次里最多用了 11 步，大部分在 6 到 9 步之间。也就是说，完成这个任务自然需要 **4 到 11 步**，而题目原本给的上限正好落在这个范围中间。所以在原上限下那 30% 的退回，原因是上限太紧，而不是「模型不知道什么时候该停」。（设计文档 5.9.2 节那句话是针对子任务助手说的，子任务一般 2 步就能完成。）

放宽过的上限记录在 `$OUT/decl/<题目>/meta.json` 里（`maxSteps`、`declaredMaxSteps`、`maxStepsOverridden` 三个字段），每次运行的输出里也会显示。

**`read {"path":"."}` 曾经会让整次运行直接失败。**
这是用 `--dump-wire` 抓下来的一次真实调用：文件视图那一层报错「需要一个路径」，变成了 `tool-threw`（工具抛出异常），结果运行在第 2 步就结束了，任务列表一个字都没写。

同一次运行还暴露了第二个问题：`assertions.action` 只告诉模型操作的名字，没说具体执行什么。于是模型在 8 步里花了 4 步去找配置文件。它猜配置文件是 `*.json`、`*.yaml` 或 `*.toml`，但实际的配置文件叫 `.fugue/config`。

这两个问题都已经修好了（`0eb34b2`、`6a0e82e`）。

**提醒「预算还剩多少」只能放在两个地方：**
一是第二段内容（B 区），每次运行放一次，对所有助手都一样；二是工具返回的结果里（属于第三段 C 区，只往后追加的部分）。

如果把一句每步都会变的提醒放在第三段的开头，后面所有内容的缓存都会失效。所以「还剩几步」这种提醒不能每一步都说一遍。这是架构文档 8.11 节「只追加」原则的要求。

**合并冲突这一步终于能走到了。**
负责拆任务的助手自己拆出的两个子任务改到了同一个文件，合并时报错「重折之后仍然冲突：`src/format.ts`」。这时 `work.json` 是空的，所以这次运行没有结果。记为「没有结果」是正确的。

**`bash` 在生成的文件树里报过 `ENOTDIR` 错误。**
出错路径是 `.fugue/mat/<agent>/upper/legacy/old-format.js`，错误以 `tool-threw` 的形式漏出了工具层。

目前代码里还没处理 `ENOTDIR` 的 `lstat` 调用只剩三处：`src/execute/reclaim.ts` 里的 `walk` 和 `leavesUnder`，以及 `src/materialize/lay.ts` 里的 `walk`。`land.ts` 的 `diskEntry` 已经明确把 `ENOTDIR` 当作「路径不存在」处理了。

**这个问题还没能复现**，先记录在这里。要解决的问题是「工具层的异常不能漏到外面」，而不只是找出哪一行漏了错误处理。
