### 序言：余烬在剪枝



上个月，Deepseek 核弹连发，不管是掀起 flash 革命的 Deepseek V4 Flash-0731，还是神鬼二象性的 Deepseek V4 Pro-0813，至少都在大家伙心里留下了深刻的印象。更不要说面向 AGI 设计，万物皆插件的野心勃勃的 Deepseek Harness 了。对我这个🐋小子来说，惊喜来的实在是太突然。我立刻动手体验了这个有趣的 Harness 框架，并测试了它的创造模式（虽然不出所料地把自己搞崩溃了）。然而噩耗来的总是那般突然，就在我兴奋地为我的个人小文件整理开源项目添砖加瓦的时候，梁文峰带着他的涨价来了。眼见着自己的费用蹭蹭上涨，上下文缓存那些钱也不由得让我心疼起来。可怜的余烬那时候还完全没有意识到，其实雷霆大思考才是上下文那么长的主因。于是我萌生了这样的想法：“要不我自己动手做个插件，把或成熟，或创新的上下文压缩机制缝进去，顺便美美收 Github 星星，投递一点大模型公司简历”。然而直到动手之前，我都还没意识到自己即将面临怎么样的“零花钱地狱”。



上下文管理是个被研究的十分透彻的领域，在通过免费快速的 Deepseek 网页快速模式 Deeeepseeeek 了一段时间后，我就笃定了自己已经对于 Harness 的上下文管理机制有了充分的了解。好！动手！结果自然是大败而归。



在 dsh-price-less 插件设计的初版，我进行了几个重大构想：**RAG/代码树为底层的语义化文件读取**，**基于意图的任务边界识别**，**任务边界与压力阈值自动压缩**，**提示词优化器**。



具体来说，任务，也就是 Task，并非特指某种类型的任务，而是针对代码的某个结构/功能，具有文件读取特征的修改。根据这一定义，我们在边界区间压缩上下文能够最大程度避免上下文失效，降低重读率，同时拒绝为原本用不到那么多次，但是一直存在于缓存中的内容，大量重复计费哪怕很廉价的缓存计价。



而任务边界唯一的判定标准，就是用户输入。每轮任务内，全量的用户输入都会进入到“任务判别器”的上下文，再被组装上“项目整体目标”作为稳定前缀，确保任务边界判别的成本极低，压缩自动化且准确。而提示词优化器则更是巧妙复用，通过 task 前上下文，当前用户输入，与安装在 Harness 中的 Skills 列表按需取用，做到将用户的提示词扩写锚定，并且对于一些 Skill 能覆盖的操作给出最优解决方案，避免试错。RAG/代码树则是语义化，细粒度地读取文件，减少盲目全读和反复重读。



设想很美好，但是现实很骨感。因为实习要求在即，我不得不把 RAG 这种复杂内容搁置，移动到路线图中，全力开发边界识别。在这期间我经历了多次失败。包括机械判定完全不准确，embedding 模型区分度极低，参数调优倾向于刀刀切，作弊获取奖励，评价标准难以综合多个指标。更不要说我作为夜猫子多次忘记梁文峰，足足烧掉了几十块的零花钱，最终才形成了上面那套能和提示词优化器复用缓存的成熟方案。



过程中还诞生了很多新的想法，包括工具剪切中间层等。通过对工具结果的保守通配，只保留有用信息，如编译器报错。但是在实测之后收益极低，最终被搁置。还有结论压缩，基于和工具剪切的类似理念，将中间结论直接代替“思考-工具调用-再思考-结论”，嵌入上下文。但是实际上，提示词注入后，大模型很难按照要求给出剪切信号，机械剪切风险和收益不成正比，也被弃用了。还有压缩产物的结构，也让我殚精竭虑。通过任务和类型化子任务高度浓缩之前任务信息固然不错，但是模型申报原文作为热尾天天坐标不准组装出错也非常令我恼火。事实上，经过一些实际使用，有限的原文长度对于模型的复读阻止作用十分有限，现在已经在本地改成申报坐标了，原文什么的，自己多读几轮，至少还更精确吧。



庸庸碌碌忙活这么久，最大的成功还是边界压缩，给我气笑了。索性还是有点安慰，至少 Kimi 可能为真的面试题，竟然句句踩在我失败的 embedding 和机械路径上，总算是长舒了一口气。不对啊？人家零花钱比我多多了，要是真试出来更好的，那还是我亏麻了，气气气！



但是这样磕磕绊绊的探索，也让我产生了一个足够疯狂的想法。已知上下文剪枝非常困难，已知上下文积累速度极高，主要来自于模型调用读取的文件慢慢积累，慢慢因为长度和中段被遗忘，然后再次读取……



我们处在一个上下文不够用的环境下太久了，以至于我们一直在思考如何做减法……那有没有可能，上下文是应该自己长出来的呢？



### 正文：欢迎来到上下文原生智能（Context-Native Agent）的世界



#### 问题的由来



所以，当我想到这一点的时候，一切就豁然开朗了。在过去，上下文极度紧缩，完全不够用的时代，我们花费了不知多少功夫，试图将海量内容塞在上下文里，通过各种索引 RAG 的方式确保模型能够瞻前顾后，将一切纳入考量，但是随着 Deepseek 家模型拉开百万上下文的普惠年代，30% 上下就开始手动压缩成为了常态（目前平衡信息量与模型能力衰减的甜点级上下文长度在 20-30%，不严谨，但是大概为社区主流观点[1][2][3]；不过新近一份编码代理的白盒实测指出，这个甜点并不是一个稳定阈值[44]），那么我们是否也该反思自己：“**上下文压缩与剪切，是否还是正确的上下文处理方式呢？**”



究其本源，我想我们要回归一个最基本的问题上：什么是 Agent？在目前的社区主流与共识的说法中：“Agent = Harness + Model”。实际上 Deepseek 甚至将这个理念写入到了他们的招聘要求中。在他们的实践中，甚至也出现了模型与 Harness 框架耦合才能解锁最高能力的现象。我对这一点其实并不持反对态度。虽然说在客观上这限制了用户 API 调用的选择范围，但是事实上这就好比人使用自己的手达成通用能力一样，这样的耦合也许有助于达成更高的能力上限。不过，当然更大的原因是 Deepseek Harness 是一款自由，开源的框架，并非是为了商业目的的强迫。



回到问题本身，Harness 本身并不是什么简单的东西，尤其是学习 Claude 成熟经验后诞生的各种千奇百怪 Harness 框架。有的内置各种 RAG，Skills，MCP，Tools，以 Agent Loop 为核心。将 Harness 视为 Agent 的组成部分诚然合理，但是这个框架太大，太重，让我们不知道如何去管理。当我们预设了每一分上下文信息的必要性，那必然就要面临顺序，取舍与重读，还有困难的剪枝。历史和实践证明，我们总是习惯性地通过补丁来解决，引入更多的机制，更多的压缩，更多的坐标。可是我在这里想要问下一句，**有没有可能，上下文是从一颗纯净、被构建的前缀“种子”中生长出来的？**



#### 换一个主体



当我们去审视大语言模型的本质，在它的视角里，并不存在什么所谓“Harness”，甚至就连思考过程都是依靠训练对齐的，它只是一遍遍地处理着语言输入的黑盒函数。**决定它输出状态的只有上下文与参数**，所有的工具调用，思考过程都是训练对齐的结果。那我想，我们应该拒绝以用户交互的对象为 Agent 主体的认知错位，事实上：**“Agent = Environment + Context + Model”**。



这句话反映的是两个层级：模型的状态只取决于参数与上下文；Agent 的状态取决于环境 + 上下文 + 模型。



#### 两条基础规则



这个主体替换，落到可操作的地方只有两条规则。

- **规则 1（信源）：** Agent 的状态住在环境里，上下文只是从状态重建出来的一份投影，不是装状态的容器。**因此一份内容能不能离开上下文，只看一件事：它离开之后还能不能从环境重建出来。** 环境里已经有的（代码、状态、依赖），随时取得回来；环境里还没有的（“这个功能落在哪些结构上”这份理解、对用户的承诺、还在成形的需求），要么先写进环境，要么不能离开——写进环境之后，那些每一步都要用到的，就被每一轮装配成上下文，**这正是前缀的来历**。

- **规则 2（判断的位置）：** 判断只允许落在有判据的地方；**没有判据的地方，一律用核对代替判断。** 压缩要求预知十步之后会不会用到被丢掉的那一行——这件事没有判据，所以它只能是一场赌；装配是照映射核对——这件事有判据，所以可以交给模型。设计里凡是出现“必须做一次判断”的位置，先问一句：这里真的有判据吗？



#### 四个推论



这两条规则直接给出四件事——

- **推论 1：** 在一个环境受控的 Harness 框架下，保存一个 Agent 所需的运行状态无需任何与当前 Context 无关内容，成本远低于“Agent = Harness + Model”的假设。

- **推论 2：** 在同一个 Harness 框架下、且环境一致时，给定上下文就能立刻重建一个 Agent 状态。

- **推论 3（普适）：** 上下文不该是 Loop Then Compress，而是按轮 **再生成 → 切片 → 合并 → 重载**（Regenerated, Sliced, Combined, Reloaded）。这一条不依赖环境：对纯对话系统（无文件系统、无进程、无副作用），它同样成立——上下文那时就是全部环境，状态同样要**以一个个可指认的单元保存下来、像文件一样被管理**（写下来、取出来、换版、弃置），只是没有需要维护的环境实体。

- **推论 3′（Agent 特化）：** 当系统存在环境实体（代码、依赖、进程、端口）时，上述四步落到具体对象上即为——**环境维持共享、代码 fork、上下文 build**。

这四个推论共同指向的并非既有框架的补丁，而是**取消了一个约束**：内容离开上下文，不再等于失去内容。在旧框架里上下文是缓冲区，离开意味着内容丢失；而在新框架里上下文是投影，离开只是此刻无需[4][5]——不过新上下文里住着两种东西：**环境里已有的**（代码、状态、依赖），离开随时能重新取出；**环境里没有的**（“这个功能落在哪些结构上”这份理解），离开就得重新读懂一遍，所以它不离开——读懂之后写下来，作为前缀被每一步廉价复用，只在合并时更新一次，靠写一次摊薄到每一轮，而不是每轮重写。**压缩/剪枝与重建的全部差别，就藏在这个等号里**。



具体来说，**构建本身是能够被规划与预测的**——重启点由任务边界给定（一个目标之内，每完成一轮归并又是一次），到点重建一次，边界内按需存取；而当内容已经垒起来、后面的东西又压在它上面时，再回头抽掉其中一段的剪枝，就显得风险过大、成本太高。构建所做的像是 CPU 的缓存预取，只是这里的“预取”要模型自己判断、自己写下来：猜偏了，也只是多背进来一点**为真却用不上**的背景信息，对任务落地几乎没有负面影响，在成本上也只是多一点——而且多出来的那部分落在最便宜的一档。可一旦构建正确，精准高效地组装了关键上下文，被省下的就不只是背着的那部分：思考与工具调用的轮次会跟着收敛，输出与缓存也随之少下去，这还没算上干净上下文本身带来的增益——它比的是基线，不是模型自身的上限（这两笔没有计进账里，见附录 2 A2.6）。然而这甚至还不是全部——在上下文的构建与组装里，**没有对与错，只有对多少与错多少；而错的代价不是损失，是少省了一部分**（这里的“错”指的是**装了为真却用不上的内容**；装进来与事实不符的东西，代价仍是做错决策，不落在这一档），于是不那么精准的装配，也能比现在的常见设计更省、更快。



最终，以上述的理念为核心，我们可以推导出下一代 Agent 范式，与其较为具体的工程实现。我称其为上下文原生智能（Context-Native Agent）。在这一架构下 Harness 的职责从管理 Model 转向管理 Context 与管理一个 Agent 运行单元所需的环境。Context 与 Harness 复杂框架解耦，作为与模型唯一的交互通道被解耦出来，**成为 Harness 的一等公民**。



#### 被换掉的是解空间



Context 成为一等公民，意味着我们在文件治理，项目管理，操作系统与软件工程的成熟经验，均可以套用在管理 Agent 状态的运行单元上，实现高度透明，机械化，有保障的 Agent 协作，助力大模型在前 AGI 时代发挥能力上限。



然而，本文真正的价值不只在 Git 树与围绕它打造的这个系统上。Git 只是一个具体实现，粗糙、可替换，甚至可能是错的。真正被换掉的是**问题的解空间**：

- 在 `Agent = Harness + Model` 下，上下文是一段必须被管理的缓冲区。所有解法因此被逼向同一个方向——压缩、裁剪、摘要、检索——它们的共同点是**都要在信息量与长度之间做取舍**；而只要做取舍，就必然丢东西，就必然要赌。补丁套补丁、坐标套坐标，都是在这个解空间里打转。

- 在 `Agent = Environment + Context + Model` 下，上下文是一份**可以从状态重建的投影**。这一步换掉的正是那个取舍：压缩是**删除**，不可逆；分区是**不构建**，可回取。既然上下文随时能从“环境 + 协议”（**协议即每个模型自己的上下文与工具拟合形状**，见附录 1）重建，不构建它就**不再等于失去内容**。这个等号一解开，压缩就不再是唯一出路——而分区、委派、构建之所以在旧框架下显得奢侈，恰恰因为旧框架里没有“可重建”这个前提。

#### 具体实现



以这一理念出发，一种上下文原生智能的具体实现可以以一种 AI native “Git tree” 为核心，其分为主 Agent 与子 Agent。对单模型串行、对“贵模型规划、便宜模型执行”，这套结构都更优；而主与子用同一个模型时更优——同一份缓存前缀在两边命中，成本结构比分模型更好，模型不一致也不影响结构成立。



对于任意一个项目，主 Agent 与子 Agent 拥有一个**共享缓存前缀**[6][7]，其为当前系统版本下，必要的意图映射汇总，与必要的系统状态。当一个任务被委派时，主 Agent 负责与用户对齐需求，并对任务进行拆分，任务拆分的具体原则以降低耦合度与提高子任务目标的内聚性为主，且对任务的规模进行控制，确保其上下文占用对齐模型能力甜点区间。



然后，其将为每个子 Agent 创建一个分支，具体而言：maintain environment, fork code, then build context as a seed。**每轮都要走一遍分叉、定契约与准备合并，这笔开销与任务多长无关**[8]。每个子 Agent 的工作会作用于分支的虚拟文件上，以提交记录的形式落盘。



任务解耦完毕后，主 Agent 将会运用其对于代码整体的理解，为每个子 Agent 委派上下文中预置的文件内容，然后由 Harness 进行**最大前缀组装**[38]。且主 Agent 会制定断言与测试作为合并前必要验收标准。



任务过程中，子 Agent 的动作可能或主动或被动提交 Signal，供主 Agent 进行环境观察与调度。也就是说，这一具体设计类似于一种响应式 Agent 调度框架。



全部子 Agent 回归后，由主 Agent/委派 Agent 进行代码合并，取长补短，并进行最终测试与汇报，并同时会对系统状态、意图映射等进行更新——由主 Agent / 委派 Agent 重写需要模型更新的部分，其余部分由 Harness 从环境**分别装配**成新的前缀[9]。（这一步重写的是**变动的那一段**，而不是**整篇前缀**：一段短，整篇长，两者的价钱差一个量级，附录 2 会算这笔账。）这个新的前缀将会成为下一次执行时候的公共前缀，其作为全局理解对于之后的主 Agent 任务委派与子 Agent 的全局观起到指导作用，是衔尾蛇循环重启自己生命历程的步骤。



综上为我为上下文原生智能（Context-Native Agent）设计的一种 Git Base 的基础架构。其具有理解与执行解耦，过程透明可理解，并行效率高，各个 Agent 可复用现有单流程 Agent 上下文管理成熟经验，前缀缓存利用率高[10][11]，且规避了上下文长度瓶颈，更是**从信息熵与上下文长度两方面让同一个模型发挥得更充分**。



#### 相对主流的优势



具体来说其相对主流，定性可能具有的优势：

- 在上下文层面：每个子 Agent 只会被给定极其干净的 [ Environmental View ] + [ Project Structure and Intention Mapping ] + [ Raw Files Assigned ]，作为其生长出果实的“种子”。这样干净的上下文有助于模型立刻进行工作，减少读取的工具调用次数和探索信息的不可控，但因为只是种子，也保留了发挥空间与一定的不可控风险。在具体的工程实现上，如果 Raw Files Assigned 段太长，则考虑仅先放入公共前缀部分，后续内容通过一个特定工具按需取用[9]。

- 在缓存利用层面：每个子 Agent 共享大量共同头，甚至 Raw Files 之前的内容可以与主 Agent 共享缓存前缀，等价于将所有只需要探索一次的内容的复利控制在了每个子 Agent 分区中，上下文累计只以子 Agent 结出的果实的形式回归主干，被吸收利用。这种共享有个前提：**装配时段序稳定**[12]——前缀为了信息密度每轮都要更新一版，但段序一动不动，变动的只落在尾部，没变的部分逐字节相同。而分支那份上下文本身并不回归，它随分支一起消失，**消失的只是“曾经构建在上下文里”，不是内容**。而根据 Git 与软件工程的成熟经验，一次合并就意味着项目意图/功能结构的变更，但**重启不必跟着合并走**：互不相干的合并先攒着，一次收拢；只有变更触及了后续计划还要用到的结构，才需要提前一次（拆分本就以低耦合为准，这种情形是少数），最终做到每个目标实现时，上下文长度几乎不触及压缩阈值，每次变更只进行一次干净彻底的探索，不带着压缩后信息密度高却丢失细节的信息包袱。

- 在透明度层面：主次分明，探索思考，需求对齐与实际落地解耦，交互均有 signal 可查，代码，架构与功能变更清晰可确认。

- 在需求表达层面：这种解耦对人是单向减负的——写对提示词的重要性下降，因为它从用户的手艺变成了架构里的一个部件。单上下文的活法里，人的意图只能靠一段话进入系统，于是“一次说全、按模型偏好的格式说、每轮复述状态、说到模型能执行的那一层”这四件事必须由人承担；在本架构下，它们分别由环境、契约、前缀与按需读回接走——状态不必重申，需求可以分批给，格式由契约规定，用户只出目标与判断。序言里那个“提示词优化器”想做的事，到这里换了一种更省的做法。**降下来的是修辞那一层，升上去的是结构那一层**（人设、格式模板、咒语／什么进前缀、段序、给哪些工具）——本文的账正是靠后一层赢的。而省下的是表达，不是判断：目标仍然要人来定，改目标也仍然要付一次重启的钱。（见附录 1）

- 在模型适配性层面：可对齐每个模型所需求的最优上下文形状。

- 在模型能力层面：主要收益来自于信息熵的降低与上下文长度可控——中段迷失与能力衰减被压住，而更短、更聚焦的上下文本身就让同一个模型发挥得更好[13][34]。

#### 边界与未来



其有待实验验证的点在于任务规模与解耦设计对于成本与能力的具体影响。但是，随着 Goal 模式等交互模式的兴起，任务的复杂度在上升，且逐渐变得更加高层，与实现无关。因此，**传统的上下文累计思路必然会受到对齐需求与探索时期复利的反噬**，哪怕是压缩之后也一样。



而对于我们这套 Git 架构，越是随着任务的规模增大与目的的实现无关，就越可以被细化为边界清晰、数量可控、架构解耦的落地分支，并由主 Agent 一次生成一份稳定的、共享的、能回答“这个功能会落在哪些结构上”的项目意图映射与清晰边界的架构契约。最终规避并行写者 N² 的冲突[14][15]，因为那是在任务高度耦合的具体实现目标下的不理想情况。当然，具体方面的优化打磨，不易解耦的任务，我们的架构能以付出轻微额外成本为代价，即可轻松回退到少分支、乃至单分支的结构上，落地仍然是委派。



我相信 **build 上下文会是上限更高，更符合未来需求与趋势的更优选择**。Git 管理只是我结合软件工程经验给定的一个具体实现，只要思想存在，就一定会涌现出更多优秀设计。而当前 Git 架构下去，困难点在于虚拟文件的编译与测试、环境稳定性维护。



而在更加遥远的未来，当大模型的输出速度成为瓶颈的时候，缓存架构的优秀是否也意味着，首 Token 和平均 Token 都能大大提高[16][17]？具有实际生产价值的模型规模上限得到扩充？不过这些都是当前架构成为主流顺带来的好处罢了，总之，它意在扭转还没有回头的迟滞当下，是面向未来以工程复杂度换取落地价值的优秀架构。现在的大模型架构革新，以收敛难度与炸炉风险换取能力上限，而 **Harness 架构的革新成本与风险，可是要小得多，难道不值得探索吗？**



### 附录 1：Harness 耦合现象的思考 与 Context 作为一等公民的必要性



**这一节说的就是正文里的“协议”。** 正文在“上下文可以从状态重建”那一步写的是“环境 + 协议”——协议指的就是下面这些**每个模型自己的上下文与工具拟合形状**，也就是 Context 从 Harness 里分出来之后，那个必须与模型对齐的兼容层。



序言里说的“神鬼二象性”，具体就落在接口面上：Deepseek V4 Pro-0813 在实际发布后饱受诟病，在除了极简模式 + 类 linux 之外的环境下，均难以产生较好的结果。在上文中，我也曾经提到了关于 Harness 作为模型原生手脚的比喻，耦合以发挥模型能力上限。**同一个模型，只换一层交互面，成绩就换了一次。**



而当我们放下个人视角，从模型训练的角度，Tools 是否有泛化的必要与泛化的可能？



在我看来，模型在 Tools 的泛化上完全没有必要进行特殊训练。对 Tools 格式的理解完全可以被通用工具，代码调用覆盖，将参数与信息量浪费在对齐可能出现的不同自定义 Tools 上面是因噎废食。我们 Harness 构造的最终目的是能力上的通用，而非不同框架下的普适，就像我们不怎么需要去训练模型写什么 Visual Basic 代码一样。



而在数据构造的角度来说，我们给模型输入的构造数据，其涵盖的 Tool 类型也必然是给定有限，优先确定，通用的优秀组合。如 Edit，Bash 等。其主要目的就是聚焦 Agent 完成任务过程中，充当眼与手。如果要增加模型对于多样工具调用的适应性，为此降低其对通用普适，且已经足够达成通用能力的工具的调用能力，显然是得不偿失的。



那么，我们所需要面临的一点问题就是 Harness 框架作为产品的独立性与市场性又该如何保证？每一家的模型在自家 Agent 上都会默认胜出，那如何通过优秀的 Harness 设计抢占市场，制定标准，把握用户数据入口？



答案就在于 Context 作为与模型直接交互的中间层。现在的通用 Harness 在 API 层实现对模型的解耦（**解耦的是调用，不是形状**），因此其不能对齐模型的训练数据与偏好环境。真正行之有效的适配方式，是在上下文组装环境为每个模型进行分野。不同的工具调用对于模型的形状各不相同，对应着模型的原生“肢体”。这样的一套通用 Agent 架构，才能实现对于同一模型，同一发挥下的“可比性”。



先前有次我问 Agent：“你的读取工具返回什么形状？” 与我预期之中它直接转述自己上下文不同，它反而反其道行之，调用了数次该工具，然后从代码里推断出一个形状。**答案本来就在它眼前，它却绕到外面去取。这是不自知。**



这个现象透射的本质是：**Agent“自知”的来源，指向的是外部的工具和 Harness 环境**。然而，一个模型不是没有状态的，它的权重就是它的状态。但是在部署的那一刻，它的状态就不再变化了，它也就化为了一个静态的切面。也就是说**它缺少的是状态的动态**：权重不更新，它就永远是“输入决定输出”，而不会因为做过什么而不同。



因此我们发明了 Harness，喊出了“Agent = Harness + Model”的口号，意图以 Harness 来补足模型的状态动态。但是这样的补全迈不过这道坎：**外赋的状态永远扩展的是广度，而没有对自己的指涉，Agent 的深度就无法进步**。一份原理写在文档里，每轮都要重新阅读；模型能用它不是因为内化理解了它，而是它“恰好”被你，被 Harness 置于上下文中。故此**真正的能力分野不在于知道多少，而在于内化和提炼**。



具体到对自己认知与框架的更新，模型的真正局限不在过程，而在于该不该的判断。**而判断，是只有我们才有的能力**：内化回答的是“是什么、怎么做”；要问“我该不该”，前提是有一个能把自己也当成对象的主语。因为只有我们自我指涉，只有我们直面了现实的局限性，承认了枚举是不现实的，进步是不可比的。



在正文中，我曾列过现在的串行对话里，我们为了拟合模型所付出的代价：一次说全、按模型偏好的格式说、每轮复述状态、说到模型能执行的那一层。我们竟称之为上下文工程。



然而，**这四件里没有一件是判断，它们全是表达**，所以它们能分别被环境、契约、前缀与按需读回接走。因此，人和 Agent 的协作，不应把所有过程压缩到 assign 中，而是 **Discuss, check and confirm**。环境与架构越干净，我们就越不必出现在流程里，而只在任务边界处，发挥为人最大的价值与权利：**不必把话一次说完，不必照着它的偏好组织语言，不必每轮重述自己已经说过的事**。 Harness 从不仅仅是 Agent 的 Harness，它更是我们的工具：**工具越像手脚，留在我们手里的就越是判断——那不是被剩下的，那本来就只属于我们。**“提示词工程”本就不该存在：它包装的是人“精于使用某种工具”的能力，而本该反过来，由工具向我们证明它自身。



原本，写到工具形状对于训练成本的时候，我就已经洋洋自得了。但是上面对于模型和人能力的进一步阐述分析，我想我又更深入了一步：Context 的解耦，最大的价值，兼容层只是一个表象而已。真正的实质是，我们把模型为了框架做的妥协，通过框架所能管理的状态外包了出去。事实上任何通过训练来对齐的形状，都是最偷懒的做法。我们太依赖模型去给出正确的形状，可是这样得到正确形状的代价，是不是未免有些太大了？但是，又如何去最小化这样的成本呢？



在 Deepseek Harness 中，我们看到了一种名为 PTC 的模式，其本质是使用代码编写替代工具调用。但是它被给定的理由是经验的，工程测算的，而不是认知性的，不禁让我有些可惜。因此在接下来，我希望从定性和原理的角度给出直观上一套简洁优雅的推断，为什么单工具是未来模型的最优方向。



在此前的元认知实验中，我们能够得知的是，对于模型而言，其 Tools 的契约形状是无法被认知的，模型所被处理被拟合的是 Tools 的实际内容。现有的 Tools 契约调用具有调用逻辑简单固定，对特定契约拟合严重的特点。事实上这带来了个两大问题：首先我们自废武功，把模型寻找自己想要的信息的逻辑限制为了简单的工具调用组合，完全没有发挥模型的通用能力上限。其次，工具和内容的推理被契约分划为了两个维度，如果想要对各自复杂度的 harness 环境和自制工具都增强泛化能力，那所需的训练数据必然大于只训练通用能力的。不然，Agent 就会产生对特定，尤其是原生工具的调度偏好。



故此，单工具最为简单的效果，便是让与 Harness 机械层的契约简化了，工具形状拟合的兼容层成本降低。而真正有价值的则在后面：

- 工具调用逻辑代码化，收摄进单工具模型内部，增强了工具调用的效果上限。模型现在使用自己最强的代码能力处理工具调用，结果更加可控，所需契约更简单，训练时候更好对齐。且分支与循环，即回收即用的工具调用结果，能有效压缩工具调用次数和结果回传思考的次数，从而让 API 调用次数下降。

- 工具调用偏好被缓解，因为模型在写代码这个维度的能力，天然就会调用所需要的函数，这是无需训练的时候特意泛化的行为，或者说这本来就是我们的设计意图。

- 代码结构具有天然的契约性，那么额外的契约训练就是不必要的，因为这个契约可以收摄到代码内部，被模型的代码能力天然处理。比方说我们无需大量的额外训练对齐，就能让模型通过返回值返回它真正需要的内容，然后将思考-工具调用链条，替换为前缀+结果的组装。因为返回值意味着模型需要，模型需要本身就是一个结论，用这个结论充当下一步所需的上下文，在定性上是成立的：**即便某次返回值不够用，被丢掉的那段原文仍在环境里，回取一次就补上**——它不是靠模型自足，是靠环境兜底。

综上所述，Context 作为一等公民所开创的解空间是丰富且高效的，让我们实现一个真正的跨模型优秀 Agent 成为了现实。



### 附录 2：半定量成本分析（已用真实账单锚定）

本节不做实验，只做账。

所谓“半定量”，是只做到**量级正确、方向可靠**，不去追一个精确到小数点的数字。

账本上守三条规矩：

1. **每个参数都取对结论不利的那一侧。**
2. **能实测的用实测值；不能实测的才取保守值，并且标明它是保守值。**
3. **算完回头查一遍：这些“保守”取法，是不是真的都在对我们不利？**

第三条不是客套。查完之后，绝大多数取法确实偏在不利的一侧，**只有四条例外**，单独列在 A2.7——它们决定了结论能走多远。

参数全部来自本地归档里三条**从未装过任何上下文处理插件**的干净原始记录：合计 9,023 步、363 小时、54 次原生压缩，逐次调用的计费数据完整保留。本节凡是写“实测”的地方，都指向它们。**其中两组数不要互相折算**：A2.0 那张账单构成占比用的是三条会话合计；**A2.3 起的账锚在一条会话上**——2,068 步、9 次**人工**压缩的那条（`session-b5f92412`），A2.5 另拿一条 455 步、从不压缩、一路顶到 70.2% 的会话当“不管控”的例子。

还有一件事要在开头说清，因为后面每个数字的读法都由它决定：**上下文是每一轮从 0 构建出来的**，“一份内容不在上下文里”是默认状态，要它出现才需要有人决定、才需要付钱。四个台阶（A2.2：同一份内容在账上的四种计费状态）正是按这个前提排的。

**再把这一节量的是什么说清楚：它是本文那处具体实现（Git 树）的账。** 参数逐项在 A2.4 交代，每一项都取对结论不利的一侧；换一处实现、换一组参数，数字会变，**而四个台阶、三个判据（三条能否掉本架构的问题）、有效残留（把重置的钱折成“常态多背多少 token”之后的可比量）这几样东西的形状不变**。所以下面的结论属于这处实现，不属于“每轮重建”这件事本身。

#### A2.0 计费模型与符号

**三档价格。** 全文按 **DeepSeek V4.1 Flash 低谷时段**计价[18][19]：

| 计费项   | 单价               | 什么时候按这一档计           |
| ----- | ---------------- | ------------------- |
| 缓存命中  | ¥0.02 / 百万 token | 这段内容没变、被缓存复用        |
| 缓存未命中 | ¥1 / 百万 token    | 这段内容是新的，或者缓存已经失效    |
| 输出    | ¥4 / 百万 token    | 模型**写**出来的每一个 token |

两个比值决定了整笔账的形状：**未命中是命中的 50 倍，输出是命中的 200 倍。** 换成一句人话：

> **模型每写 1 个 token 的钱，等于把 200 个 token 背着走一步。**

**这句话不是修辞，它的量级由实测的用量撑住。** 把三条实测会话合计 9,023 步的 token 量按上面这张价格表算一遍[20]：

| 钱花在哪          | token 量   | 花费     | 占比        |
| ------------- | --------- | ------ | --------- |
| 背着（内容没变，命中复用） | 1,817.1 M | ¥36.34 | 38.5%     |
| 第一次读新内容（未命中）  | 20.5 M    | ¥20.50 | 21.7%     |
| 写（模型输出）       | 9.41 M    | ¥37.64 | **39.8%** |

平均每步：背 203,660 个、写 1,043 个。**写量只有背量的 0.51%，花的钱却是背的 1.04 倍**——这就是 ¥4 与 ¥0.02 那 200 倍价差落在真实用量上的结果。

这张表还澄清了一个容易滑过去的说法。**按单价，背着确实极便宜；但真实任务里背的量是写量的 200 倍，于是两者在账单上各占约四成。** 所以准确的说法不是“背着不要钱”，而是：

> **背着的便宜，正好被它庞大的数量抵消掉了；而写只用了 0.5% 的数量，就换来了同等的账单。**
> 
> 所以这两笔钱哪一笔更要紧，不能先验地断定——这也正是下一节必须一条一条算的原因。

**而这个差别，本质上是有损与无损的差别：**

|           | 重置时要**写下来**什么                                 | 结果                                          |
| --------- | --------------------------------------------- | ------------------------------------------- |
| 基线（有损压缩）  | **内容**：把这个区间里“以后可能还要用”的东西概括成摘要                | 摘要必须承载语义，所以写得长                              |
| 本架构（无损卸载） | **变动的映射**：只写需要模型更新的那一段（意图映射、系统状态），原文仍然在 git 里 | 映射只是索引，所以写得短；而且原文**本来就不必待在上下文里**，要用的时候读一次就行 |

注意“写下来多少”和“上下文里占多少”是**两件事**：摘要和映射都要占据上下文（这部分只是被**读**，便宜），但只有“写出来”的那一步按输出价计费。

| 符号                  | 白话含义                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| 窗口 $W$              | 一个模型一次请求最多能装多少 token。本文一律按 100 万 token（$W=1\mathrm{M}$）举例。                                              |
| 压缩                  | 装不下了，就让模型把已有内容读一遍、写一份更短的摘要，再用这份摘要替换掉原来那一段。                                                              |
| 残留 $L_{0}$          | 一轮刚开始、上下文刚构建完的那一刻，里面装了多少 token。基线的残留是 $C_{c}$（摘要 + 保留的尾部），本架构的残留是 $P+s$（前缀 + 切片）。                       |
| 残留 $C_{c}$          | 基线压缩之后留在上下文里的那些内容（摘要 + 保留的尾部）。实测中位 15.3k，账面取 15.2k。                                                     |
| 重读段 $C_{r}$         | 基线压缩之后**第一次还要重新读一遍**的那一段。它不是残留：残留里有一部分字节仍在缓存中。实测均值 9.2k。                                                |
| 触发点 $\theta$        | 上下文涨到“窗口的百分之几”的时候触发一次压缩。$\theta=50\%$ 就是“装到一半就压”。                                                       |
| 步数 $T$              | 模型的一次“思考 + 动作”算一步，整个任务一共 $T$ 步。                                                                         |
| 每步新增 $g$            | 每一步平均往上下文里新增多少 token。                                                                                   |
| 前缀 $P$              | 所有分支、所有轮次都用、而且内容稳定的那一段：人设与工具清单、项目结构说明、意图映射（哪个功能大致落在哪些结构上）、必要的系统状态。注意 $P$ 是它**在上下文里占多少 token**，是一个“读”的量。 |
| 更新量 $M$             | 主 Agent 为了更新前缀，**真正写出来**多少 token。因为只写需要模型更新的那一段，$M$ 通常远小于 $P$。                                          |
| 构建                  | 每一轮开始时，Harness 照当时的环境把这一轮要用的内容装配成上下文。它不花输出钱，只让模型多读 $P$ 个 token。                                         |
| 切片 $s$              | 只发给某一个分支的那部分文件内容。                                                                                       |
| 不在上下文里（默认）          | 一份内容没被构建进这一轮上下文的状态。这是默认状态：不花钱，也不需要谁做决定。                                                                 |
| 边界                  | 一轮结束、一个分支退出或整个任务收尾时，那一轮的上下文整体消失。原文都在 git 里，消失的不是内容。                                                     |
| 摘要长度 $\sigma$       | 基线每压缩一次，模型要**写**出来多少 token（摘要 + 思考）。                                                                    |
| 命中价 $p_{h}$         | 内容没变、被缓存复用时，读一个 token 的单价。本文取 ¥0.02/M。                                                                  |
| 未命中价 $p_{m}$        | 内容变了、缓存作废、必须重新读一遍时的单价。本文取 ¥1/M。                                                                         |
| 输出价 $p_{o}$         | 模型**写**出来的 token 的单价。本文取 ¥4/M。                                                                          |
| 重发现 $\rho$          | 被摘要丢掉的信息，后来又被用到，只能重新推导一遍。每一步平均要重新推导的量记作 $\rho$。                                                         |
| 压缩间隔 $k_{b}$        | 基线的两次压缩之间隔多少步。                                                                                          |
| 轮长 $L$              | 本架构里，**一个分支**走满一轮需要多少步。                                                                                 |
| 轮数 $R$              | 本架构一共分多少轮。每合并一次、并重建一次前缀，算一轮。注意一轮里有 $N$ 个分支并行，所以按总调用数摊算是 $R=T/(N\cdot L)$，**不是** $T/L$。                  |
| 分支数 $N$             | 一轮里同时开多少个分支。                                                                                            |
| 协调开销 $\varepsilon$  | 本架构比基线多出来的步数比例（定契约、委派、写断言这些步）。                                                                          |
| 每次重置成本 $E$          | 一次“重置”要花的钱。基线是 $E_{b}$，本架构是 $E_{d}$。                                                                    |
| 有效残留 $R_{b},R_{d}$  | 把“每次重置要花的钱”折算成“相当于常态多背多少 token”，再加到残留上，得到一个两边可比的量。**有效残留小的那一方更省。**                                      |
| 差额 $\Delta$         | 两套架构**每一步**平均占用的 token 数之差。                                                                             |
| 平均占用 $\overline{L}$ | 两次重置之间，每一步平均背着多少 token：$(L_{0}+\theta W)/2$。两条路线都用它算“背着”那一侧的钱（见 A2.2）。                                  |
| 前缀变动量 $\Delta P$    | 新一版前缀里**真正变了**的那一段有多少 token。段序稳定时它落在前缀尾部，前半段照旧命中缓存。                                                     |
| 重发现盈亏平衡点 $\rho^{*}$ | 基线的重发现量 $\rho$ 涨到多少，才会把本架构的成本优势吃光。                                                                      |

#### A2.1 两套架构的成本来源构成

**基线（传统累积 + 边界压缩）的成本来源**

| #   | 类别  | 来源         | 具体是什么                                   | 随什么增长                               |
| --- | --- | ---------- | --------------------------------------- | ----------------------------------- |
| 1   | 背着  | 过时内容被反复重读  | 早就没用了的中间结果还留在上下文里，后面每一步都要重新读它一遍         | $T^{2}$（完全不压缩时）／$T\cdot k_{b}$（压缩后） |
| 2   | 重置  | 压缩把缓存打掉    | 压缩会把替换点之后的上下文全部重写，缓存作废，之后只能按**未命中价**重新读 | $(T/k_{b})\times C_{c}$（未命中价）       |
| 3   | 重置  | 写摘要        | 每压缩一次，模型就要写一份摘要，还要先想一遍，**这是输出价**        | $(T/k_{b})\times\sigma$             |
| 4   | 重置  | 重发现        | 摘要丢掉的细节之后又被用到，只能重新推导一遍，**同样是输出价，而且不封顶** | $\rho\cdot T$                       |
| 5   | 背着  | 压缩这个动作要读输入 | 压缩时必须把被替换掉的那一段重新读一遍（多数是命中价）             | $(T/k_{b})\times$ 区间长度              |
| 6   | 背着  | 探索不受控      | 上下文越长，越容易在中段丢信息，模型乱找路的概率越高              | 表现为 $T$ 和 $\rho$ 都变大                |

**本架构的成本来源**

| #   | 类别  | 来源     | 具体是什么                                                                                                                                                        | 随什么增长                                          |
| --- | --- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------- |
| 1   | 固定  | 分叉     | 每一轮做一次 git 操作，给分支切一份代码                                                                                                                                       | $R$，**固定、极小**                                  |
| 2   | 重置  | 定契约    | 事先说好每个分支要产出什么、边界在哪里。它在上下文状态上与合并只差一条提交记录，因此和合并算同一件事                                                                                                           | 与合并同项                                          |
| 3   | 重置  | 合并与解冲突 | 两个分支改到同一批文件时要解开冲突，成本由这种重叠的程度决定                                                                                                                               | $N^{2}c$                                       |
| 4   | 重置  | 更新前缀   | 主 Agent **只重写需要模型更新的那一段**（意图映射等），其余各段（人设与工具清单、系统状态）由 Harness 从环境取出，**分段装配**成新一版前缀。写出来的量是更新量 $M$，按输出价；装配出来的 $P$ 是被“读”的，走命中价，**只有每版变动的那一段 $\Delta P$ 才付一次未命中** | $R\times M$（输出价）＋ $R\times\Delta P$（未命中价，每版一次） |
| 5   | 背着  | 回归测试   | 改完跑一遍测试，确认没有弄坏原有功能                                                                                                                                           | 与基线相同，两边抵消                                     |

**关键观察：这套账里只有两种钱——“背着”和“重置”。** “背着”单价极便宜（¥0.02/M），“重置”极贵（¥4/M，是前者的 200 倍）。基线的重置有三项（2、3、4），其中重发现（第 4 项）不封顶；本架构的重置只有一项，而且**写的是变动的那几段、不是整篇内容**，所以它的量级是 $R\times M$ 加上每版一次的读，而不是 $R\times P$。

**还有第三笔钱：第一次读新内容，实测里它占 21.7%。** 每一步产生的工具结果、用户消息，都是全新内容，第一次读必然未命中，之后才转为命中。它在两套架构里都存在，因此**做差时会抵消掉**，不进结论；但它不是零——“背着 + 重置”这两笔并不是全部账单：同一张表上，第一次读新内容自己就占 21.7%。

**还有一件比这两笔钱更根本的事：本架构省下的钱，大头不是“少写”，而是“根本没构建”。** 基线把一份内容构建进上下文之后，想让它出来，只有压缩一条路。本架构里，内容默认就不在上下文里——要它出现，得先有人决定构建它。**需要判断的问题于是从“该丢什么”变成了“该构建什么”**，而后者是照着映射就能核对的事。下一节把这条差别折成四个价码来看。

#### A2.2 两种钱、四个台阶

这套账里只有两种钱：**背着**（内容装在上下文里，每一步都要被读一次）与**重置**（上下文换一版时，我们必须写下一点什么——基线写摘要，我们写变动的那一段）。

但往下看之前，得先接受一个前提——后面每个数字的读法都由它决定：

> **上下文不是攒出来的，是每一轮从 0 构建出来的。**

模型自己不带记忆。每一轮递过去的上下文，都是照着当时的环境**重新构建一份**，而不是把前一轮接着往下续。所以在这套架构里，**“一份内容不在上下文里”是默认状态**——不需要谁做决定、不需要动作、不花钱；反过来，**“它在上下文里”才是那个需要理由的状态**：得有人决定把它构建进来，付一次它头一回被读的钱，然后在此后的每一步继续为它付钱。

这个前提一摆出来，两条路线的差别就不再是“谁删得更聪明”，而是**“谁需要删”**。基线把内容构建进去之后，想让它出来只有压缩一条路：一次有损的、必须做判断的、要付三笔钱的动作。本架构里没有这个动作——内容默认就不在里面，要用才构建，用完回到默认。**序言里记的那三次翻车（工具剪切收益极低、结论压缩拿不到模型的剪切信号、压缩产物的坐标不准导致组装出错），全都是“做减法”时翻的车；减法在这套架构里根本不存在。**

**一份内容在这一生里，会在四个不同的价码上各停一停**，而它们的单价差着两个数量级：

| 台阶  | 这份内容在做什么                              | 单价        | 折合“背着”多少步 | 属于哪种钱   |
| --- | ------------------------------------- | --------- | --------- | ------- |
| 一   | **被写下来**（写摘要与写更新同档）                   | ¥4 / M    | 200 步     | 重置      |
| 二   | **第一次被构建进上下文**（构建过又离开、之后再取回来一次，也是这一档） | ¥1 / M    | 50 步      | 背着（未命中） |
| 三   | **此后每一步都被读一次**                        | ¥0.02 / M | 1 步       | 背着（命中）  |
| 四   | **根本没被构建进去**（原文留在 git 里，要用的时候读一次）     | **0**     | 0 步       | 不付      |

第四列是这张表最有用的一列——它把“贵不贵”换算成了同一个尺子。**写一次的钱，等于把它背 200 步；构建一次的钱，等于把它背 50 步。** 于是对**已经构建进来的**每一份内容，该留还是该走只看一件事：**它下一次被用到，大概在多少步之后。** 五十步以内还会用到，就让它留着（继续待在台阶三）；下一次用到在五十步以外，就让它走（回到台阶四），到要用的时候再构建（台阶二）——只有那种每一步都得被参考的东西，才配一直停在台阶三。

只要一份内容还留在上下文里，模型每一步就必然要读它一次——台阶三收的就是这笔钱。所以“不构建”不是省钱的小技巧，它是一条判据：

> **对每一份内容挨个问一句：它值不值得此后每一步都被读一次？**

值，就一直背着（比如那张“这个功能会落在哪些结构上”的意图映射）；不值，就让它用完之后回到“不在里面”的默认态，要用的时候再构建。

**我们的纪律只有两句，它们管的是两件不同的事：**

- **第一句管“写”和“构建”：每一份内容，台阶一只付一次、台阶二只付一次。** 一份原文尽量不要这一轮写一遍、构建一遍，下一轮又写一遍、构建一遍。这也是“把它写进前缀”比“反复按需读取”划算的原因——前缀每一轮都装配在同一个位置、逐字节不变，于是它只在第一次（或它真正变动的那一次）付台阶二，之后每一轮都直接命中。
- **第二句管“留”：构建完就让它走，除非它值得此后每一步都被读一次。**

**“一直背着”和“只付一次的未命中钱”因此并不矛盾**：一直背着的只能是那几样每一步都要看的东西（前缀），其余的只构建一次。**而基线的病根，正在于这两句它一句也做不到**——每压一次就把新残留整段重读一遍（台阶二付了又付），同时把一大堆积压内容一直背到触发点（台阶三也一直付）。实测里换轮时的缓存失效（占全部未命中 token 的 34%–43%），就是前一句的账单。

**先算“背着多少”。** 上下文在两次重置之间，是从“残留”一路涨到“触发点”的。如果每一步新增的量大致固定，那它就是一条直线；而一条直线在这一段里的平均值，正好等于两端的中间值：

$$\overline{L}=\frac{L_{0}+\theta W}{2}$$

| 符号             | 白话含义                | 基线                                | 本架构                               |
| -------------- | ------------------- | --------------------------------- | --------------------------------- |
| $\theta$       | 触发重置时，上下文占窗口的比例     | $\theta_{b}$：**实测中位 31%**（见 A2.3） | $\theta_{d}\approx 20\%\sim 30\%$ |
| $L_{0}$        | 一轮刚开始、刚构建完时的残留长度    | $C_{c}$（摘要 + 保留的尾部）               | $P+s$（前缀 + 切片）                    |
| $\overline{L}$ | **每一步平均带着多少 token** | $(C_{c}+\theta_{b}W)/2$           | $(P+s+\theta_{d}W)/2$             |

**因为两次重置之间是直线增长，这个式子不含可调参数：它是算出来的，不是拟合出来的。**

**实测校验：这个式子对得上量级。** 干净会话实测每步平均占用 208,853，式子算 $(15.2\mathrm{k}+310\mathrm{k})/2=162.6\mathrm{k}$，低估约 22%（反过来说，实测比式算高约 28%）——因为增长并不均匀，用户换轮时也不重置时钟。偏差在两边以同样方式存在，不改变比值，只让本节给出的**绝对金额整体偏低**。

于是两边每一步“背着”的差额是

$$\Delta=\frac{(\theta_{b}-\theta_{d})W+(C_{c}-P-s)}{2}$$

整个任务里“背着”这一侧的差额，换算成钱就是 $T\cdot\Delta\cdot p_{h}$。

**再算“重置一次多少钱”。**

基线重置一次，要写一份摘要，还要把压缩后新拼出来的上下文第一次读一遍：

$$E_{b}=\sigma\cdot p_{o}+C_{r}\cdot p_{m}$$

其中第一项是**写摘要**（输出价），第二项是**新内容第一次读**（未命中价）。第二项只按**压缩后真正要重读的那一段** $C_{r}$ 计，**它不是残留 $C_{c}$**：压完保留的残留里有一部分字节仍在缓存中——实测九次压缩后首次调用的未命中均值是 **9.2k**，而残留的中位是 15.3k。

本架构重置一次，要写一份更新（只写变动的那一段），还要让分支把这一版新前缀读一遍——**未命中只付一次，不按分支数付**：

$$E_{d}=M\cdot p_{o}+\Delta P\cdot p_{m}+(P-\Delta P)\cdot p_{h}$$

第一项是**写更新**（输出价）。第二项要拆成两半，因为**前缀是分段装配出来的**——模型只重写该由模型更新的那一段，其余各段由 Harness 从环境取出：

- 被重写的那一段 $\Delta P$，缓存作废，按未命中价付；
- 没变的那些段 $P-\Delta P$，字节没动，**照旧命中缓存**，按命中价付。

只要装配时段序稳定（本设计要求的正是“重写不重排”），没变的部分就一直躺在缓存里。而且这一版前缀只在**第一个分支的调用**上付这一笔，之后所有分支、所有轮内步骤全部命中——所以它按“前缀版本数”计，**不按分支数计**。

**基准档在这里取最不利的一侧：**整段前缀按未命中算（$\Delta P=P$）。真实机制是只有变了的那一段 $\Delta P$ 失去缓存、没变的那段照样命中——本设计的“重写不重排”正是为后者写的；两者的差额见 A2.7。

#### A2.3 基线不能“想压就压”

**基线的触发点 $\theta_{b}$ 不是一个可以随便拧的旋钮。** 它要压低水位，手段**只有压缩**，而压缩是花钱的动作。两次压缩之间只隔

$$k_{b}=\frac{\theta_{b}W-C_{c}}{g}$$

步。触发点压得越低，这个间隔越短，压缩次数涨得越快。于是基线手上有两笔方向相反的钱：

| 基线把触发点压低        | 哪一笔变便宜                      | 哪一笔变贵                                |
| --------------- | --------------------------- | ------------------------------------ |
| $\theta_{b}$ 下降 | **背着**的钱按 $\theta_{b}$ 线性减少 | **重置**的钱按 $1/(\theta_{b}W-C_{c})$ 上升 |

两笔一平衡，就得到基线自己会选的那个最优触发点：

$$\theta_{b}^{*}W=C_{c}+\sqrt{\frac{2gE_{b}}{p_{h}}}$$

代回去，基线能压到的最低总成本是：

$$C_{b}^{*}=T\cdot p_{h}\cdot R_{b},\qquad R_{b}=C_{c}+\sqrt{\frac{2gE_{b}}{p_{h}}}$$

**这里的 $R_{b}$ 读作“有效残留”**——它把“每次重置要花的钱”折算成了“相当于常态多背多少 token”。

**现在把实测值代进去。** 用干净会话量出来的 $g=1{,}460$、$C_{c}=15.2\mathrm{k}$、$E_{b}\approx$ ¥0.029，基线自己的成本最优触发点是

$$\theta_{b}^{*}=\frac{C_{c}+\sqrt{2gE_{b}/p_{h}}}{W}\approx 8\%$$

**也就是每 45 步压一次、一个两千步的任务压 46 次（这是把 $\theta_{b}$ 压到 8% 时的间隔；31% 时是 202 步，见 A2.4）。而实测是这样的**——干净会话里每一次压缩我全取出来了，全部由人手动触发，丢弃量由 Harness 自己报出：

| 触发时占用    | 丢弃 token | 压完保留   | 丢/留      |
| -------- | -------- | ------ | -------- |
| 23.5%    | 165,397  | 14,585 | 11.3×    |
| 29.3%    | 206,478  | 15,489 | 13.3×    |
| 52.4%    | 433,498  | 14,427 | 30.0×    |
| 35.2%    | 242,800  | 15,011 | 16.2×    |
| 32.5%    | 244,932  | 13,834 | 17.7×    |
| 44.7%    | 333,979  | 17,933 | 18.6×    |
| **5.9%** | 27,203   | 15,334 | **1.8×** |
| 20.2%    | 115,939  | 15,486 | 7.5×     |
| 30.9%    | 178,092  | 15,908 | 11.2×    |

> **表内两个口径不同，横向加不起来：**“触发时占用”是那一刻**整个请求**的占用，还含人设与工具清单、环境视图这些**不进消息历史**的部分；而“丢弃 / 压完保留”是 Harness 对它自己那份**消息历史**报出的数——两者的差额各次在 16.5k–76k 之间。

触发占用中位 **30.9%**；九次总共丢掉 194.8 万 token，每次只留 1.5 万。

**注意唯一那一次 5.9% 的压缩：丢/留比掉到了 1.8×。** 占用已经很低时人就不再压了——不是不想省钱，而是**再压就真的没有东西可压了**。

> **8% 这个“成本最优”成立的前提，是把 $\rho=0$ 和“丢掉的东西一文不值”两条假设推到极致。它数学上成立，工程上等于算出了一条“把球砸向地板再弹进篮框”的轨迹——它把任务继续执行所必需的那些上下文当成了零。**
> 
> **九次里，那个能看见任务的人九次都不同意这个判断：他停手的位置，中位数是 30.9%。**

按实测，这句话应该这样写：

> **20%–30% 是能力上的要求（实测：人停手的位置中位 30.9%）；而只有有损压缩这一件工具时，钱算出来的均衡在 8%。两者的差，就是“压缩税”的实测大小——写摘要、缓存作废后的重读、以及丢掉的细节日后被重新推导，这三笔合起来的一道税，它大到没有人敢去领。**

**本架构的式子形状与基线完全一样。** 我们也要重置，重置成本是 $E_{d}$（见 A2.2）。它由三件事决定，**每一件都不是估计，而是这套设计本身决定的**：

1. **写的是变动的那一段，不是整篇内容。** $M$ 是模型每轮写出来的更新量，$\sigma$ 是摘要量。摘要必须承载语义（“这段区间里以后还要用的东西**是什么**”），映射只承载结构（“这个功能**落在哪些结构上**”）。**不在上下文里的那些内容，原文还在 git 里，所以不需要把它们写进上下文。**
2. **一次重置服务 $N$ 个分支。** 一轮里 $N$ 个分支并行推进，而合并与重建前缀在这一轮结束时只做一次。按总调用数摊算，我们的重置间隔是一轮的 $N\cdot L$ 次调用（本节参数下 384 步，而基线是 202 步），**约一半**；而这一次重置的钱由 $N$ 个分支分摊。
3. **未命中只付变动的那一段。** 前缀没变的部分照旧命中缓存（这一条的分量由 A2.7 算清楚）。

**在实测参数下，我们单次重置反而更贵：** 因为我们的残留（$P+s=60\mathrm{k}$）是基线残留（$C_{c}=15.2\mathrm{k}$）的四倍，而每换一版前缀就要把它读一遍——**单次重置 ¥0.060，比基线的 ¥0.029 贵一倍。** 我们赢回来的是**频率**：基线每 202 步重置一次，我们每 384 步（$N\cdot L=4\times96$）一次。两边相乘之后，重置这一侧基本打平（¥0.32 对 ¥0.30）。

**所以这套账的胜负不在重置，而在“背着”。** 而我们“背着”更少的唯一原因，是我们能合法地站在更低的水位上——这句话在 A2.4、A2.6、A2.7 里会反复出现，因为它就是全部结论。

最优触发点满足同一个形状的式子：

$$\theta_{d}^{*}W=(P+s)+\sqrt{\frac{2gE_{d}}{N\,p_{h}}}$$

**于是两套架构被放进了同一个式子里：谁的有效残留更小，谁就更省。**

$$R_{d}=(P+s)+\sqrt{\frac{2gE_{d}}{N\,p_{h}}}\quad\text{对比}\quad R_{b}=C_{c}+\sqrt{\frac{2gE_{b}}{p_{h}}}$$

**对照“基线自己的钱最优”（8%）：那时它 ¥3.33，我们 ¥5.70，我们贵 71%。** 而那条路要求它每 45 步压一次、一个任务压 46 次——实测里人压了 9 次。**这不是一个“它随时可以选”的选项，这是 A2.3 里那条“砸地板进篮框”的轨迹。**

**把几个最要紧的假设单独拎出来看：**

| 情形                            | 我们的成本     | 对真实基线 ¥7.02（省幅） | 对不管控基线 ¥16.97（省幅） |

| 基准：20%、更新 10k、4 分支            | ¥5.70     | 省 19%           | 省 66%             |

| 不并行（$N=1$），其余同基准              | ¥6.67     | 省 5%            | 省 61%             |
| 不并行 **且** 前缀按命中计价             | ¥6.25     | 省 11%           | 省 63%             |
| 更新 2k + 前缀按命中                 | ¥5.42     | 省 23%           | 省 68%             |
| 双重悲观：整篇手写 20k **且**不并行        | ¥7.53     | **贵 7%**        | 省 56%             |

**两条读法：**

1. **只有在“模型整篇手写前缀”并且“完全不并行”同时成立时，我们才会输给真实基线**——而这两件事正是这套设计本身否定的。（$N=1$ 单独发生时不构成失败：基准档下仍省 5%，前缀按命中计时省 11%。）
2. **两边都按在 31% 时，我们反而贵 12%。** 这不是算错，是这套账的结构决定的：**我们的残留（$P+s=60\mathrm{k}$）是基线残留（$C_{c}=15.2\mathrm{k}$）的四倍。本架构的钱，全部赚在“能在低水位上干活”这一件事上。** 而这一行是**算法核对**，不是两套架构各自会在的位置——低水位对基线不可达，高水位对我们没必要（理由在 A2.7 第二条）。

**胜负由什么决定。** 把两边并排，只有三个量能动。

**一、我们自己的残留 $P+s$ 有一个明确上限。** 令两边的有效残留相等，解出我们的残留最多可以多大：

$$P+s<C_{c}+\sqrt{\frac{2gE_{b}}{p_{h}}}-\sqrt{\frac{2gE_{d}}{N\,p_{h}}}$$

| 更新量 $M$ | 前缀计价  | 残留上限 $P+s$ |
| ------- | ----- | ---------- |
| 2k      | 命中    | **63k**    |
| 10k     | 命中    | 42k        |
| 10k     | 整段未命中 | 34k        |

**读法：这条线跟着更新量与前缀计价走——判据一、二都成立时（更新量回到现实的 2k、前缀按命中计价）是 63k，本节保守取的那一档（10k ＋ 整段未命中）只有 34k。也就是说：按最保守的取法，我们赢不下基线的纸面最优点（见 A2.7 第三条）；而在设计主张成立的那一档，保守取的 60k 卡在 63k 线内，只剩 3k 余量。** 这条线不是装饰——它意味着**“前缀能不能比摘要更省地表达全局”是本架构的生死线**，而不是一个可以无限膨胀的容器。

**二、更新量 $M$ 的盈亏平衡点约 2.8k。** 当前缀按缓存命中计价，只要每轮写出的更新不超过 2.8k，我们就赢；而它的现实量级就是**一步的输出**（实测每步输出 833–1,133 token）。**但如果前缀整段都按未命中计，这道式子无解**——那时 $E_{d}$ 里光“把前缀读一遍”就是 ¥0.02，已经超过每一版前缀能负担的重置上限 **¥0.0115**（$P+s$ 取 60k 时，由 $R_{d}<R_{b}$ 解出），**无论更新量多小我们都赢不了**。这一笔在 A2.7 里单独交代。

**三、重发现 $\rho$ 的盈亏平衡点是 160–194 token/步。** 按实测参数，我们领先真实基线约 ¥0.00064–0.00078 每步，而 $\rho$ 走输出价，于是

$$\rho^{*}=\frac{0.00064\sim0.00078}{p_{o}}\approx 160\sim194$$

（单位：token / 步。这正是那笔在账单上从来不会单独列出来的钱——因为它伪装成了“模型正在思考”。）

实测里压缩之后的追赶峰值到过 **1,553 与 4,983 token/步**（九次压缩中有六次测不出追赶，两次很明显）。所以 $\rho$ 不是一个“符号对不对”的问题，**而是一个量级相当的真实风险**：只要基线平均每步多花 200 个 token 重新推导，那 19% 就被吃光了。

**$N$ 与成本的关系最容易被高估。** 按前缀命中计，**$N$ 只在更新量 $M$ 大时才重要**：$M=2\mathrm{k}$ 时，$N$ 从 1 涨到 4 只带来 2 个百分点的差别；$M=10\mathrm{k}$ 时带来 9 个百分点。**开分支的理由因此落在能力、隔离与可回滚上，而不是成本。**

于是判据变成三个**具体的、可以被否掉的问题**：

> **一、每轮更新前缀时，模型真正“写出来”的是变动的那一段（不超过 2.8k token），还是整篇前缀（20k token）？**
> 
> **二、装配前缀时，段序是否稳定到“没变的那半段能一直命中缓存”？**（这一条决定生死，见 A2.7）
> 
> **三、“前缀 + 切片”能不能压在 63k 以内？**

第一条正是本文序言里已经走过的路——**从“申报原文”改成“申报坐标”**。第二条的分量最容易被低估。第三条是规模的暴露面。

#### A2.5 规模变大之后：三推一反

A2.3 的两个闭式里有两个容易被忽略的性质，先说清楚，因为它决定了趋势该怎么谈：

- **任务长度 $T$ 只是一个共同乘数。** 两边都随 $T$ 线性放大，所以 **$T$ 不改变胜负方向，只放大结论**。**“任务会变长”本身不是论据**——这一点必须先说清楚，否则会给人“我们是靠任务长赢的”错觉。
- **窗口 $W$ 不进入最优总成本。** 因为 $W$ 变大时最优触发点会跟着往下走（$\theta^{*}$ 是解出来的，不是定死的），两边的最优总成本里都没有 $W$。**“百万窗口”对双方的最优解既不帮忙也不添乱**——它惩罚的只是**死守某个固定百分比、不调参**的用法。

**那么“规模变大”到底改变了什么？** 把实测数据摊开看，是**三推一反**。

**推力一：失控的基线会一路右移到 80%。** $\theta_{b}$ 不是一个常数，它是“**谁在管上下文**”的产物。实测里能清楚看到三种活法：

| 活法                   | 触发点          | 每步平均背着 | 一次 2,068 步的账单 |
| -------------------- | ------------ | ------ | ------------- |
| 程序员手动压（能看见任务）        | 31%          | 162.6k | ¥7.02         |
| 完全不管控                | 撞 dsh 默认 80% | 407.6k | ¥16.97        |
| 纯按钱调（纸面点：串行不拆分，它站不住） | 8%           | 47.8k  | ¥3.33         |

实测里那条**从不压缩、455 步一路顶到 70.2%** 的会话，就是“不管控”长什么样；同一批数据里，照上表的口径，“不管控”与“有人管”的每步成本差 **2.4 倍**（¥16.97 对 ¥7.02）。**用户越多、任务越杂、越没人盯上下文，基线就越往右边那一档滑。**

**推力二：摘要的容量不随规模增长，而任务必需的上下文会。** 实测里残留恒定在 1.3–1.8 万，与任务多大无关——因为它是**模型一次写出来的、长度固定的摘要**。任务一大，被丢掉的细节就多，$\rho$ 就往上走，而 $\rho$ 按**输出价**计费（是背着的 200 倍）。**这一条是结构性的，不依赖任何参数，也是本架构最硬的论据。**

**推力三：用户级的任务天然可并行。** 实测 $N=1$——程序员在 2,068 步里一次子代理都没开。用户级任务（多来源、多方案、多文件）天然能切片并行，$N>1$ 会变成常态。不过 A2.4 已经算过：**$N$ 只在更新量 $M$ 大时才重要**；$M$ 一小，$N$ 就退居次席。

**反方向一：我们的残留 $P+s$ 也会随规模增长。** 这是唯一的暴露面。基线不管任务多大都只留 1.5 万；我们的前缀随代码库涨、切片随任务面涨。A2.4 给的线是 63k——**所以“前缀能不能比摘要更省地表达全局”，是本架构能不能随规模一起赢的分水岭。** 而这条线管的是**每一轮都构建进上下文、此后被反复读**的那些东西：切片可以按需取用（A2.6 第 6 条），所以真正要长期盯住的其实是前缀 $P$。

**于是趋势的落点很具体：不是“任务变长”，而是三件事——基线会不会失控、$\rho$ 会不会涨、我们的残留会不会跟着涨。** 前两件对我们有利，第三件是风险。

#### A2.6 没有计入账里的收益

A2.4 的账里有几笔明显对我们有利的钱，**不是在账里被设成了零，就是被按最笨的活法算了一遍**。把这几笔加回来，就是下面这些——**不在账里计，但应当被知道**。**先说清这一节的性质：它是“未计账的收益”清单，其中多数是方向性证据，它不构成“我们能在 20% 的水位上正常工作”的证明**（那件事还没有做，见 A3.5 第三条）。

**（1）平均上下文更短，注意力更集中。** 本架构每一步的平均上下文长度比基线低 $\Delta$（按实测参数：触发点从 31% 降到 20%，平均每步少背约 33k；对完全不管控、一路撞到 80% 的基线，少背约 278k）。上下文越长、模型判断质量越低是可复现的现象。**而更短、更干净、更聚焦的上下文，是同一个模型更接近它自己的水平**——相对基线是能力上的更强，相对模型自身的上限则是把被拖走的那部分拿回来，不是把上限抬高：同一批问题只给相关部分（约 300 token）优于给全量（约 113k token）[1]，后者正是被拖累的那一侧；实测里人停手的位置中位 30.9%，也说明 20%–30% 是能力要求而不是舒适区。**这条主张有边界、也有反向证据（干净上下文只在开头挡得住继承来的杂乱），见 A3.3 相应那一行。**

**（2）中段迷失被结构性规避。** 长上下文里，处在中间位置的信息最容易被忽略。切片把工作时的上下文限制在 20%–30%，中间段本身变短，“中间”这个位置不再显著。

**（3）基线必须做一次“丢什么”的判断，我们这边根本没有“丢”这个动作。** 压缩丢的是**没有被计划过**的信息——你无法预知摘要丢掉的那一行会不会在十步之后被用到，**因此不可补偿**。而切片只是**没有被构建进去**：没构建不等于丢了，原文还在 git 里，主 Agent 随时能把它读回来（按需读取），或者干脆把它写进前缀。**压缩这一步必须判断丢什么，而且丢错了无法挽回；分区不需要这个判断——“构建什么”本身就是可以机械核对的。** 这是两条路线最本质的差别，且不依赖任何参数。**这笔差别可以标价。** 基线那九次压缩一共丢掉 **194.8 万 token**；如果要把丢掉的内容重读一遍、核对摘要是否忠实，按未命中价算是 **¥1.95**——相当于它整张账单 ¥7.02 的 **28%**，而且这笔钱不带来任何收益，只用来让那份摘要变得可信。本架构没有这个动作：它的“校验”就是把该装的内容装出来，**顺带完成，不额外计费**。

**（4）没有有损压缩，因此没有重发现。** 基线的 $\rho$ 来自被摘要丢掉、之后又被需要的细节。本架构里，一个分支做完就退出——它的上下文跟着分支一起消失，但**消失的只是“它曾经被构建在上下文里”这件事，不是内容本身**（原文仍然留在 git 里，什么时候要就什么时候读）。既然没有任何东西被删掉，也就没有“重新推导一遍”这笔钱。

**（5）探索受约束，路径更收敛。** 分支启动时拿到的那一小段内容（环境视图 + 结构意图映射 + 委派文件）限定了分支的起点与范围，减少盲目通读和随机试错。这同时降低了 $T$ **和 $T$ 的波动幅度**——而波动变小在成本上是双份好处：既减少平均返工，也减少做工期估算时必须留的余量。**这一条在 A2.4 的账里被设成了 $\varepsilon=0$（协调开销为零），但它的真实符号是负的**：前缀越准，分支越不需要自己找路，总步数 $T$ 反而比基线更小。

**（6）切片不必整段预先构建。** A2.4 的账里，切片 $s=40\mathrm{k}$ 是按“每个分支每一轮都把整段 40k 构建进上下文”算的。但设计本身允许另一条路：只把公共前缀放进去，剩下的文件交给一个工具**按需取用**——没被取用的部分根本不进上下文，于是一路停在台阶四；被取用的部分才走台阶二与台阶三。**这是“从 0 构建”最直接的推论：默认是不构建，构建才是那个需要理由的动作。** 这笔钱能省多少，取决于“分支实际需要取用多少”，我们既没有实测，也不打算把它计进账里，但它说明 A2.4 那个 $P+s=60\mathrm{k}$ 的残留，保守的成分不只是“取大”，还有“假设了最笨的构建方式”。

**（7）更短的上下文直接换成延迟与吞吐。** 本架构每步背着的内容更少，而且每一轮的前缀逐字节相同，于是 prefill 更短、缓存复用更充分。这一层不是我们独有的：[17] Mooncake 量到前缀缓存命中带来的吞吐与延迟收益；[37] KVFlow / KVCOMM 在工作流感知的前缀复用下，多智能体并发仍取得 prefill 与吞吐收益；[16] Splitwise 给出 prefill 与 decode 的耗时比——1,500 输入 token 的 prefill ≈ 6 个输出 token 的 decode。三条都属**甲档**（来源等级见 A3.0）。**这一项按 A2.4 的取法不计入结论**（“不拿时间上的好处去补贴成本上的主张”），但不该被当成不存在。

**（8）装配可以有多不精准。** A2.4 的两套账之间留着 ¥1.32 的余量（¥7.02 − ¥5.70）。按命中价折算，这笔余量允许本架构**每一轮多装约 3.2 万 token 的无关内容**——而正常装配是 $P+s=60\mathrm{k}$；也就是说，**装配里有过半是废料，账上仍然赢**。代价的斜率是命中价而不是未命中价，前提是这些废料也必须“稳定地废”（每轮抖动的内容按未命中计价，贵 50 倍）。不过账上容得下不等于注意力容得下：衰减跟的是绝对 token 量，所以真正的上限是 63k 那个预算，不是这 3.2 万。

**（9）跨模型的那条分工，不靠“把计划再发一遍”。** 常见的分工是贵模型规划、便宜模型执行：计划每轮重新生成或重新递一遍，执行侧读到的是一份跨模型拼起来的上下文，没有一个能一直命中的缓存单元。本结构里贵模型写下的是一份**短、稳的前缀**，此后每轮只重写变动的那一段；执行侧读的是**逐字节不变**的同一份字节，于是**各自模型内部都能一直命中**。**主与子同模型时，这份前缀还能在两边共用；不同模型时少的只是这一层**（见 A3.6）。这一条是定性比较，没有进账：本文的账算的是同模型那一档。

**（10）对用户说过的原话可以无损留着，因为它不必再当上下文。** 累积式的活法里，对话本身就是上下文，窗口一满就得摘要——被摘要掉的常常是“当时为什么否掉了另一个方案”这类没被计划过的信息，偏偏用户日后最可能回头引用的就是它。本架构里对话不是上下文：主 Agent 每轮从环境重装，而“用户说过什么、我说过什么”重装不出来，**所以它只能以原文的形式待在环境那一侧**（正文那句“上下文随时能从环境 + 协议重建”，对对话那一段要成立，前提正是它），像任何一个文件一样**按需回查**——没被查到的部分根本不进上下文，查到的也只是命中的那几段。**留档因此可以无损，不是因为我们更小心，而是因为对话已经不在窗口里了。** 这与本文反对 append-only 日志并不冲突：反对的是**把日志当上下文**，不是**有日志**；这份存档只用于回查，与“视图从环境重装”正交。它同时是正文那条“写对提示词的重要性下降”的兜底——**人敢说得随意，是因为说漏了还能回头查；查不到，人就会退回一次说全。** 按 A2.4 的取法这一条不计入账（它不省 token）；它占的上下文只有环境视图里一行恒定声明，不随对话增长。

#### A2.7 四条例外

前面每一处取法都取在对我们不利的一侧，只有四条例外：两条不是保守取法，而是**假设**；一条是取法本身越过了真实机制；还有一处是**公式值与实测值之间的取舍**，方向同样偏在有利的一侧。它们必须单独说清，否则上面的结论会被读得比它实际支持的更强。

**一、$N=4$ 不是保守值，它把“设计被正确使用”当成了既定事实。** 实测是 $N=1$——那条两千步的干净会话里，人一次子代理都没开。在基准档下，这一条把结论从“省 19%”拉到“省 5%”；在前缀按命中计的档位下，从“省 20%”拉到“省 11%”。

**二、$\theta_{d}=20\%$ 是能力假设，不是成本结论——而基线那一侧的 8% 连假设都不是。** 本节所有“省 19%”都建立在“我们能在 20% 的水位上正常工作”之上，这一条不在算术里：**A2.6 给的是方向性证据，完整的证明还没有做**（见 A3.5 第三条）。但“两边的最优点都落在 8% 一带”这个巧合，不该被读成“基线也能跑到那里”：**基线只有一层上下文，理解与干活挤在同一段内容里；串行又不拆分，它就不可能不带着足量的信息工作。**压到 8%，省下的正是它干活所必需的那部分理解——A2.3 已经把那个最优点成立的前提写清了：把 $\rho=0$ 与“丢掉的东西一文不值”推到极致。所以 8% 对基线是纸面点，不是可选的工作点。

**低水位在我们这里为什么成立，是同一条道理的正面。** 全量理解在前、拆分在后：理解被**编译**成那份稳定前缀（短、稳、每一步都在），干活只装自己那一片，缺什么按需读一次。**低水位不是设计出来的，是拆分出来的；而拆分的前提是先有一次全量理解。** 基线没有这两层可分，只有一层，所以它一低就丢能力。

**“两边都按在 31% 时我们贵 12%”因此只是一道算法核对**，不是任何一方会选的位置：真要那么跑，等于我们主动放弃唯一的机制优势。

**三、前缀整段按未命中，是一条越过了真实机制的取法。** $E_{d}$ 里的前缀项本该拆成两半：变了的那一段 $\Delta P$ 失去缓存，没变的那段继续命中。取 $\Delta P=P$ 等于假装每换一版都要整段重读，差额是 $P(p_{m}-p_{h})=20\mathrm{k}\times(1-0.02)/\mathrm{M}$，也就是 **¥0.0196**。

它单独看只占我们总成本的 1.9%（¥0.11 / ¥5.70），看起来无关紧要——**但它进的是开方号里的 $E_{d}$，于是被放大成“我们能不能赢下基线自己的最优点”这件事**：

| 取法             | $E_{d}$ | 我们的有效残留 $R_{d}$ | 对基线 $R_{b}=80.5\mathrm{k}$ |
| -------------- | ------- | --------------- | -------------------------- |
| 前缀整段未命中、更新 10k | ¥0.060  | 106.8k          | **输**                      |
| 前缀按命中、更新 10k   | ¥0.040  | 98.4k           | **输**                      |
| 前缀整段未命中、更新 2k  | ¥0.028  | 92.0k           | **输**                      |
| 前缀按命中、更新 2k    | ¥0.008  | **77.5k**       | **赢**                      |

**单改前缀的计价还不够，必须同时把更新量从保守的 10k 放回现实的 2k，$R_{d}$ 才能压到 $R_{b}$ 之下。** 而这两件事恰好都是这套设计本来就主张的：**只写变动的那一段而不是整篇（小 $M$）＋ 段序稳定（前缀可缓存）。**

**这里要留意一点：因为每一轮都是从 0 构建，“段序稳定”这句话的分量比它看上去大**——它决定的正是“上一轮构建在同一位置的那几段字节，这一轮还在不在同一个位置”。在，就继续命中；不在，就整段按未命中重读一遍。**而这份差额的方向是清楚的：把前缀按真实机制计价，只会让我们更便宜。** 本节“省 19%”用的仍是保守档，没有靠它。

**四、压缩间隔取了公式值 202 步，而实测是 230 步——这一条取舍偏在我们有利的一侧。** 两次压缩之间隔多少步，直接决定基线压多少次、付多少次重置的钱；间隔越长，基线越便宜。表中两个值都给了，我们用了 202。影响很小：基线的重置从 ¥0.26 涨到 ¥0.30，整张账单从 ¥6.99 到 ¥7.02，省的比例从 18.4% 变成 19.0%——**0.6 个百分点**。但它的方向确实是偏的，所以必须在这里露面：**A2.0 的第三条规矩问的正是“这些保守取法是不是真的都在对我们不利”，这一条就是那次复查漏掉的。**

第三条不是偏向哪一边，而是**越过了真实机制**；第四条相反，它偏了方向，但量级已经交代清楚。本节的立场因此是这样：

> **在能把差值算清楚的所有项目上，我们几乎都取了对自己不利的一侧；四条例外里，三条不是取法问题，而是这套设计能不能兑现的假设——它们成不成立不在账上，要看 A2.6 那批方向性证据（完整证明还没有做）；剩下一条是压缩间隔取了公式值，偏在有利的一侧 0.6 个百分点，已单独交代。**

#### A2.8 本节结论

**不看公式，只看这件事：**

1. 主流做法是“把内容都攒在上下文里，装不下了就写摘要、把原文删掉”。删掉的东西以后还要用，就只能重新想一遍——**而“想”是按最贵的价格计费的。**
2. 这套做法是“每一轮都从空手开始，照着清单去仓库取这一轮要用的东西”。清单上写的是**要什么**、不是**东西是什么**，所以写起来很短；取回来的还是原件，用完就放手——**它回到的是“不在上下文里”的默认态，而不是被删掉了。**
3. 于是困难的问题换了：**从“该丢什么”变成“该构建什么”。** 前者必须由模型做一次判断，判断错了无法挽回（序言里那三次翻车都翻在这里）；后者写的是映射，照着映射就能核对装对了没有。**这套账里省下的钱，大头不是“少写”，而是“根本没构建”。**
4. 在这个价位上，“写”极其昂贵：**模型写 1 个 token 的钱，等于背着它走 200 步。** 实测里模型每步只写 1,043 个 token（是背着量的 0.51%），却付出了和“背着”一样多的钱——**账单里有四成，就花在这 0.5% 的量上。**

**看数（一次 2,068 步的真实任务，全部账在 A2.4）：对实测的真实基线省约 19%，对完全不管控的基线省约 66%；对照“基线自己的钱最优”（8%），它比我们便宜 71%，而那一档要求它一个任务压 46 次、实测里人只压了 9 次，而且串行不拆分的结构根本站不住那一档（A2.7 第二条）；“两边都按在 31% 时贵 12%”是算法核对，不是我们会在的位置。**

> **成本这一侧，两套架构的账形状相同，差别全在“那条水位线能不能站住”：基线必须带着足量的信息干活，压到它自己的钱最优就等于放弃理解；而我们要站在低水位上，靠的是理解与干活分了两层——先全量理解，再拆分。它在账上表现为 19%，在能力上表现为 A2.6 那九条，其中第一条就是：更短、更干净、更聚焦的上下文本身就是更强。**

---

要把本节从“半定量”推到一张可以直接对照的账单，还差三个数：**每轮更新前缀时真正写出的更新量 $M$**、**“前缀 + 切片”的真实残留 $P+s$**、**契约成本的分摊情况**（第 1 轮 vs 后续轮）。这三个数要由一次对照实验来量——对照组直接要求完成一个中等规模开源仓库的改造任务，实验组用本架构手动组装前缀并委派。

**“核验”一栏**：`原文` ＝ 逐字读过原始页面或论文正文；`转述` ＝ 原始页面未能直接访问，数字经镜像、索引或第三方转述核实（完整说明在 A3.7 末条）。

**正文里“最大前缀组装”的“最大”**指的是两件事：**共享的字节最多**（同一个前缀单元被尽可能多的调用命中），并且**保住文件本身的结构性**（对齐模型训练时见到的 tools 格式，见附录 1）。它不是“装得越多越好”。

#### A3.2 相似架构对比与区分

有几项工作与本文看起来高度相似，必须逐条说清分界，否则“内容离开上下文也不丢”这层会被误读成本文的贡献。

**这张表要读成一张分区图：**它们绝大多数是在“累积下来的上下文里做减法”，本文换掉的是信源。

| 工作                              | 它的机制                                                   | 与本文相同的那一步             | 与本文的分界                                                                             |
| ------------------------------- | ------------------------------------------------------ | --------------------- | ---------------------------------------------------------------------------------- |
| **MemGPT / Letta**[31]          | 主上下文 + recall/archival 外部存储；被逐出的消息写回外部存储，用时按语义检索取回     | 内容离开上下文不等于失去内容        | 外部存储放的是**模型自己写的记忆与消息历史**，取回靠**语义检索**；且它是**累积**的，本文每轮**重投影**                        |
| **LCM**[29]                     | 分层摘要 DAG 压缩旧消息，但保留**指向每一份原文的无损指针**                     | 无损指针，摘要只作索引           | 它保的是**对话**的原文指针；本文不保留对话，只保留**环境**，上下文由环境重新推导                                       |

**分界线只有一条：信源。** 上表每一项都要求“**对话历史被保存下来**”——它们的无损，是无损地指回那份历史。本文要求的是“**环境是权威源，对话可以丢弃**”，所以上下文不是被裁剪出来的，而是被**重装**出来的。这一条差别决定了两件事：一是不需要另建一个原文库（git 已经是），二是“每轮从零重装”才成立——它们不能重建，因为没有可重建的权威源。

#### A3.5 至今没有人做过的对照

**这一栏划出引用管不到、只能靠实验回答的部分。它要测的是解耦本身，不是某处实现的好坏。**

**一、把“机械 vs 模型”控制住之后，再比“累积 vs 重建”。** 现有文献里，机械清除[23]与重建架构从未在同一条件下同台。对照应当是四臂，**且 B 与 C′ 必须使用同一种现成的机械手段**，否则又是拿“有”比“没有”：

| 臂      | 内容                           | 它单独回答什么                       |
| ------ | ---------------------------- | ----------------------------- |
| A      | 累积 + LLM 压缩                  | 现行默认                          |
| B      | 累积 + **厂商级现成的机械清除**          | 机械能否打平模型判断                    |
| C      | 每轮从环境重建 + 共享前缀               | 机械清除在**重建**架构下的收益（与 A→B 的差对照） |
| **C′** | 每轮从环境重建 + 共享前缀 **+ 同一种机械清除** | 本文的完整形态                       |

**A 对 B 切出来的是本文与别人共享的那部分原则；B 对 C′ 切出来的才是本文自己的增量**——这两臂机械手段完全相同，唯一剩下的变量是“上下文是累积的还是每轮重建的”。

**二、“压缩税”没有任何直接测量。** 现有文献里没有任何来源把“模型写摘要”这一笔单独计成账；最接近的净额数据是 Augment 的“每步 −75%、总量 −14%”[26]，而 ACON[43] 报的也是峰值 token 降 26–54% 这个**总账**，没有单列压缩本身的开销。所以本文把它算成一张账单，**是本文自己的贡献**，引用只能提供方向性支持，不能提供数值背书。

**三、“前缀更准 ⇒ 更少工具调用”这条因果没有任何论文测过。** 附录 2 A2.6 第 5 条把它写成设计意图是对的；但它至今是**待测**项。

**四、“N² 写冲突”是本文的用词。** 冲突现象被反复观察到（A3.4），但没有文献这样命名或量化它。

**五、体验这一侧，本文没有给出判据，也没有任何对照。** 成本侧压成了三个可复算的数（A2.4 末），不确定的那部分单独列了四条例外（A2.7）与本文自己的待测项（见本节第三、六条）；体验侧至今只有零散的好处条目。至少三个问题只能靠用户实验回答，本文一个都没有测：用户说漏了、说含糊了，能不能低成本收回？**用户能不能预期“过了这一步它还记不记得”？**用户能不能不描述、直接指着某个东西说“照那个来”？尤其第二个——“内容没丢、上下文丢了”是这套架构最反直觉的一点，对用户却是纯粹的感受问题；没有判据约束它，它就只会以“偶尔的困惑”的形式出现，永远进不了账。

**六、附录 1 的两条推断都还没有量级对照。** 一条是**返回值作为“结论”是否足以支撑下一步**（附录 1 末条）：它在定性上成立——返回值意味着模型需要，需要本身就是结论——但“省在哪一档、省多少”没有量级对照。另一条是**为工具形状做拟合训练，所需数据量是否真的大于只训练通用代码能力**（附录 1）：这是一条关于训练量的方向性断言，至今无人对照。两条问的是同一件事——**把契约从训练里搬走，代价降在哪儿、降多少，还没有人量过。** 另外，**“同一个模型、只换一层交互面”这个对照也还没有人做过**——附录 1 开篇用的那个观察是动机，不是对照（见 A3.7）。

| 对话原文无损留档、按需回查                                      | A2.6 第（10）条               | 这是**体验层的保证，不是正确性保证**：检索是词法匹配，只在用户喊出当时那个词时有效，换了说法、只记得大意就查不到，**查不到时不编**。它不进 A2.4 的账（不省 token），也不改变“上下文从环境重装”这一层——这份存档只用于回查，不是上下文的来源。留存策略与访问控制属工程细节，本文不规定。另外，**存档可查不等于会被查**：检索的键由用户给出，而模型未必会走那条路（见附录 1）。                                            |

**还有一条边界不在账上。** 正文“边界与未来”说这套架构“上限更高”，指的是**成本结构与解耦程度的上限，不是学习速率的上限**。环境承载知识，不承载学习速率：外部状态每轮都要重新经过一次读的过程，变不成会自己跑的东西（见附录 1）。本文的架构不提供可塑性——它买的是重装成本，不是让模型变得更会；权重不更新这件事，本文既不解决，也不假装能靠环境绕过。

#### A3.8 一句话

> **本文的价格模型与“背着是账单最大的一笔”有官方口径、独立研究与厂商原话三重支撑；“无损可回取”这一层已有先行工作，本文的区别在信源是环境而不是对话历史；而本文真正的成本主张——压缩税——至今没有被任何人直接测量过，所以它是本文自己的账，不是引文的结论。把“机械 vs 模型”与“累积 vs 重建”分开的那张四臂对照，也还没有人做过。**

**但“还没有人做过对照”不等于“没有支持”。** 这套设计的每一步单独拿出来，都已经有甲、乙档证据：不让模型决定下一步的固定阶段胜过自由探索[41]，单步取回胜过反复迭代[42]，外部清单胜过模型自检[44]，厂商的官方口径也已经转向“让工具结果离开上下文”[47][48]。**本文缺的不是支持，是把这些支持拼成“每轮重建”的那一次对照。**
