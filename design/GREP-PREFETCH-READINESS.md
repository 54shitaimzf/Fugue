# 完整验证命中时的整批预取省略

可选索引流水线已经保留按完整 Git 对象地址、原生正则 source/flags 验过的完整结果。重复查询仍会预取同一批源 blob，再从验证缓存读取结果。本单元只允许**整批原候选都有完整证明**时省略这次源预取；缺省未选索引的宿主沿用原路径。

`readyGrepBatch` 是工具实现内部的非加载证明，不向 `ToolHost` 加字段。它拥有一次最多 128 个原候选路径的稠密快照，捕获当前 View base/rev 与原生正则，然后仅查询 `View.stat`，确认每条路径当前的完整 BlobId 都有对应的完整记录。不读源内容、不装载索引、不触发构建、不安装记录，也不触碰 LRU 顺序。当前批面对空缓存时直接回退，不增加元数据探测；查询后续批已有记录时，即使这次查询最初是冷的，也可能发生有界失败探测。

证明在候选过滤**之前**覆盖原批的每条路径。过滤等待结束后立即再检查精确宿主/原读口/原预取函数、base/rev、原生正则和全部记录的存续。任何缺失、记录淘汰、代变化、非文件、坏对象地址/大小、未知正则或包装过的读口/预取口都走原预取；部分命中不压缩路径，也不翻译覆盖前缀。逐文件消费仍保留等待后的当前状态检查，过期证明不能提供旧的负结果。

省略预取也保留原来的 **4 MiB 元数据前缀**。实际预取与完整命中路径共用 `prefetchPlan`：相同的文件/id/大小判定顺序、相同的首次超限位置和 `covered` 数值。证明只接受原批的有序子集，宿主只在真实预取源仍是构造时那一个函数时提供这份非加载规划器。`execute` 对规划出的计数与实际回传的计数应用原来的同一段裁剪逻辑，包括首项超限时至少读一项的前进规则。

没有完整记录的正向早停、`files_with_matches` 提前返回、错误地址内容及容量超限均不能建立该证明。原生 global/sticky 正则也不参与。选了索引但有新模式或混合命中时，失败的证明会增加有界元数据探测；这是要测量的成本，不能用热命中的收益称所有查询变快。128 是路径数上限，记录/源/物理 IO 的既有预算各自有效；本单元不声明 RSS 上限或冷索引目标达成。

验证：`node tools/test-entry.js fast src/tools/grep-prefetch-ready.test.ts src/tools/grep-verifier.test.ts src/tools/prefetch-prefix.test.ts`。控制覆盖整批命中的各输出模式、一个原候选缺失而被过滤的情形、部分/错误地址记录、模式与读口回退、元数据等待及候选过滤等待中改变 View/读口、记录淘汰、有序子集和包装预取口，以及 160 个 72 KiB 文件的 128 候选批次：省略源读取仍保留原 4 MiB 边界与完整回执。真实 Git/宿主端到端验证和测量由独立控制补上。
