# 视图的字节与对象地址

`Entry.blob` 与 `Lower.putBlob` 沿用 0.2.7 的接口。对象地址由 Git 决定；视图负责让上层字节、交给对象库的字节和记录的 delta 来自同一份输入快照（架构 § 8.3、§ 9.3）。

旧实现会在复制写入字节以后，把调用者的原数组交给异步 `putBlob`。调用者在等待期间修改数组，便能让 `Entry.bytes` 保留旧内容而 `Entry.blob` 指向新内容。按这个地址读取的完整索引可以合法排除新对象里没有的字串，却漏掉视图旧字节里的匹配。此外，`Buffer.slice()` 共享存储：修改输入、读结果或 delta 的字节，会在不推进修订号的情况下改变上层内容。

现在写入和 `applyDelta` 在第一个等待点之前捕获字节与路径、模式等标量；应用时交给对象库的内容与安装的条目保持一致。复制使用 typed-array 的内建可见窗口，产生独立的 backing buffer，避免 `Buffer.slice()`、自定义 getter 或 slice 覆写改变复制语义。上层读结果与 `diff()` 的字节也各自拥有存储。复制回来的 Buffer 保留现有的 UTF-8 `toString()` 行为；公开类型仍是 `Uint8Array`。

下层复制上来、快照种子和日志重放同样拥有保留的内容。快照条目、修订点、日志起点与重放事件的标量在下层等待前捕获，避免等待后用新的标签配旧内容。这不把下层变成不可信对象库，也不声明并发写操作是事务：下层仍须兑现请求地址对应的真实字节，日志与对象库的持久化次序仍按 § 9.3 执行。

持久化接缝 `applyEdit` 也在第一个等待前拥有整条输入 delta；钉入日志的下层文件内容拥有独立存储。这让检查、对象写入、日志追加与最后的内存应用使用同一份内容和标量，即使调用者在 `putBlob` 或追加日志期间修改原输入，日志重放与活视图仍一致。该接缝与视图共用一个复制实现。

验证：`node tools/test-entry.js fast src/view/ownership.test.ts src/view/view.test.ts`。六个新控制覆盖 Uint8Array/Buffer 的等待中修改、完整 delta 输入捕获、读和 diff 的 backing buffer 修改、快照、重放及下层复制。以完全相同测试加载官方 `ba4d239` 的 `view.ts` 时六项全部失败；修复后六项及原有十一项通过。真实 Git 对象和可选索引的端到端验证由独立的 real 测试执行，不能用这里的内存对象库代替真实 Git 证明。

另外两项控制分别在对象写入和日志追加处暂停真实接缝，修改 Buffer 与 Uint8Array 输入后比对对象内容、日志标签、活视图与新视图重放。只撤回 `applyEdit` 的输入快照时，这两项都会失败。
